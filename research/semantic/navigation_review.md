# 语义导航：文献对照与实现审查

核对日期：2026-09-17。范围是面向 LingTu 实机迁移的定向工程调研，
不是穷尽检索或系统综述。论文结果、当前代码事实、迁移建议分别列出。
本文件不是已安装能力清单。未新增模型依赖，也未发送机器人运动命令。

## 先确定要解决的任务

| 任务 | 成功条件 | 不能替代成功的信号 |
| --- | --- | --- |
| 去已保存的地点 | 当前地图中的对应地点、原生任务到达 | 文本名称相似、地图版本过期 |
| 找一类物体 | 到达可观测位置，并确认目标类别 | 检测器单帧命中、全局路径非空 |
| 找特定实例 | 类别、属性、房间或关系约束均匹配 | 看见任意一把椅子 |
| 寻找暂时不可见的目标 | 有界探索、重新观测、明确成功或失败 | 永久绕圈、不断重复旧目标 |

### 需要读到方法细节，而不是照搬项目名字

SG-Nav 的重感知有明确过程：接近候选物体，多视角采样，结合检测置信度
与附近子图信号累积可信度，在限定步数内决定接受或放弃。论文的实验参数
`N_max=10`、阈值 `0.8` 属于它的离散导航设置，不能直接解释成我们 10 帧
DDS 数据或经过校准的 80% 概率。我们应使用不同观测时刻/视角的证据，
区分遮挡与反证，不能让重复缓存帧充当多次确认。
[原文第 3.3、4.1 节](https://arxiv.org/html/2410.08189v1)

VLFM 作者明确展示了检测假阳性和缺少语义线索时的失败。因此单独增加
VLM 前沿热度图不能解决“认错物体后停在错误位置”；目标核验需要独立处理。
[作者的失败案例说明](https://naoki.io/portfolio/vlfm.html)

SysNav 作者页面把房间选择、提前结束、目标验证分成查询，并报告其模型
查询延迟和频率；它使用预取减少等待。这支持我们的架构选择：模型推理
放在低频语义层，结果绑定任务版本，实时避障始终由原生链路负责。
这是迁移建议；其统计不能作为本项目的延迟或成功率承诺。
[作者的运行时说明](https://cmu-vln.github.io/)

SysNav 的成功条件还要求：机器人停下的位置能观察到满足全部语义约束的目标，
且距离符合要求。因此“有路径到物体附近”仍不能报告“找到了”。论文的
190 次实机实验跨不同本体；其中 112 次定量实机实验使用轮式平台，不能称为
190 次 Go2 验证。[任务定义与实验设置](https://arxiv.org/html/2603.06914v1)

其 Go2 分支使用 MID-360、360° 全景相机，板上 NUC 与外部 RTX 4090 电脑协作。
这不是 S100P 离线推理的性能证据；当前迁移只借鉴职责分层和观察点思想，
没有复制 ROS 运行时或加入模型依赖。[官方仓库](https://github.com/zwandering/SysNav)

## 当前代码的实际情况

- `config/runtime_graph/products/nav.yaml`：没有 `semantic_planning`。
- `inspection.yaml`：声明 `semantic` 和 `semantic_planning`。
- `tracking.yaml`：有视觉跟随，但明确禁止 `SemanticPlannerModule`。
- `modules/semantic_planner.py`：地点意图、场景快速匹配、记忆查询、恢复调度存在；
  接口通过消息进入 `nav.goals`，不应直接发送底层速度。
- 私有 `FrontierScorer` 未连接地图输入、提取、评分流程；服务适配器的局部
  正确性不等于这一运行链已经接通。
- `SGNavReasoner.evaluate_target_credibility`、`GoalResolver.verify_and_reselect`
  没有运行时规划器调用。辅助类存在，不能称为已实现语义目标确认闭环。
- 场景目标已经通过原生 request/task ID 关联回执与终态。已保存地点到达后
  报完成；有跟踪实例的物体到达后进入有界视觉核验。没有物体实例的记忆、
  前沿目标仍报 `TARGET_VERIFICATION_REQUIRED`，不能解释为物体已找到。
- `GoalResolver.resolve` 的通用异步快慢路径目前不在 Module 的物体查找流程中；
  Module 调用的是 `fast_resolve`。符号地点的 LLM 请求是另一条已接线的路径，
  不能混称为通用物体推理已贯通。

### 本轮复现并修正的代码问题

| 范围 | 触发条件及后果 | 修正 |
| --- | --- | --- |
| 任务切换 | 跟随或新指令继承旧场景目标 | 新指令清理目标；只有场景解析分支保留活动指令 |
| 地点路由 | 地点已下发或拒绝后，场景回调又重新解析同一句话 | 已处理的符号命令退出场景重解析 |
| 数据时效 | 相机/感知停止后，仍按接收时曾有效的缓存发目标 | 使用缓存时重新检查时间与坐标系 |
| 恢复归属 | 空闲规划器响应其他来源的失败 | 无活动场景指令时不发恢复请求 |
| 异步恢复 | 旧 LLM 恢复返回后重试、取消或把新任务标成失败 | 恢复结果校验指令版本 |
| 位置上下文 | 两个同类候选未获得机器人位置，选到远处候选 | Module 和服务均传入真实位置 |
| 策略接口 | 异步解析调用不存在方法、前沿评分参数错误 | 使用现有真实 API；不添加兼容方法 |
| 前沿输出 | 把 `center_world` 误写成 `position`；失败记录调用不存在方法 | 正确传递坐标和失败记忆 |
| 动作服务 | ndarray/字典混用、接近距离参数不匹配、环顾多传参数 | 服务转换坐标；每次接近距离显式传递且不修改默认值 |
| 动作恢复服务 | 同步方法被错误 await、参数错误；无模型时忽略失败次数 | 在线程中执行同步恢复；保留规则退避/终止结果 |
| 恢复模型接线 | 读取不存在的 `_llm` 成员，配置的模型客户端实际没有传入 | 使用 GoalResolver 已配置的 `_primary` 客户端 |

### 深查任务反馈时补齐的修复

| 问题 | 实际触发与后果 | 修复与验证入口 |
| --- | --- | --- |
| 取消没有任务编号 | 原生接口拒绝；语义层却继续更新状态 | 目标、回执、取消与终态按 task/request ID 接线；取消 ACK 不冒充已停下 |
| 状态归属错误 | 其他来源的失败、旧目标到达、迟到 ACK 干扰当前任务 | 真实 GoalService 账本验证后转发；当前语义目标再核对身份和顺序 |
| 恢复互相打断 | 原生还在恢复或暂停，场景刷新又发新目标 | 等本目标原生 FAILED 后才触发语义恢复；恢复/暂停期间保留目标 |
| 冷却期丢失败 | 新目标唯一一次终态落在冷却期或上次 worker 返回前 | 延后处理；worker 退出时处理新的失败目标，不依赖重复广播 |
| 拒绝被成功文案覆盖 | 同步拒绝后，解析层又报 RESOLVED/VECTOR_MEMORY/EXPLORING | 先发布候选选择状态，再由实际回执决定最终状态 |
| 取消后重新启动 | 取消等待中收到 FAILED，下一帧重新发目标 | 结束当前场景指令；未知恢复策略也进入统一终止分支 |
| 过期坐标重试 | 恢复模型等待期间感知断流，直接重发旧位姿 | 重试重新解析新鲜场景；地图版本/原生运行重启使缓存失效 |
| 视觉与几何任务竞争 | 跟随切换成地点目标，或每帧重新触发视觉搜索 | 显式结束旧视觉接管；切换后旧几何终态不覆盖视觉状态 |
| JSON 限制参数丢失 | JSON 目标入口忽略限速和到达半径，直接服务入口正常 | 两种入口都传递并验证 `max_speed_mps`、`acceptance_radius_m` |
| 地图/里程计混用 | map 物体位置与 raw odom 机器人位置一起计算距离，重定位后可能选错物体 | 接入感知输出的同步 map 位姿；缺失、过期、错误坐标系时暂停选目标 |

### 继续沿感知到执行链路发现的问题

| 问题 | 后果 | 修正及验证 |
| --- | --- | --- |
| 物体中心被当成机器人目标 | 可能指向物体内部或使用桌面高度作为行走高度 | 分离 ObjectTarget 和观察位姿；沿物体周边提议至多 8 个同层位置，由原生只读路径 RPC 筛选 |
| 历史轨迹被重新盖上当前帧时间 | 未再次看到的旧物体通过时效检查 | 跟踪器保存实际采集时间，合并轨迹时保留最新观测时间；导出时不改成场景刷新时间 |
| 物体编号与关系编号不一致 | 物体编号替换为二维 track ID，空间关系、房间仍引用原编号 | 场景图保留持久物体编号；当前检测流保留独立二维 track ID |
| 旧物体借用了邻近物体的图像框 | 历史记录看似有当前图像证据 | 仅对跟踪器确认本帧匹配到的物体附加图像框和特征 |
| 最近的旧候选挡住新候选 | 选中旧物体后停在拒绝状态，即使另一同类物体当前可见 | 在快速匹配前过滤过期候选和失效关系；原场景记忆不删除 |
| 预检跨越任务或地图变化 | 慢 RPC 返回后下发已取消或旧地图的目标 | 预检返回时核对指令版本、地图上下文、目标位置和位姿时效；原生失败可立即进入新的重试 |

回归包含真实 PerceptionPipeline 与 InstanceTracker 的连续帧处理，复现了
关系引用失配；观察点测试经过真实 Commands RPC 表面，仅替换原生端。
另有真实线程的慢预检，覆盖停止、替换、换图、原生重启、目标移动/消失和位姿过期。
这些证据不包括原生规划算法实跑，也不证明候选位置有良好的相机视线。

只替换原生命令端和模型调用。覆盖暂停、拒绝、超时、乱序、替换、停止和地图变化。
额外入口为 `tests/nav/services/test_goal_service.py` 和
`tests/lingtu/assembly/test_semantic_nav_command_wiring.py`。
这是本地契约证据，没有新增实机安装、运动或模型识别准确率证据。
本次相关回归共 854 项通过、1 项预期失败；另有一条 jieba 的

## 下一步迁移顺序

已接入的到达核验使用实际处理过的彩色图像、同帧检测框与 map 位姿。
请求包含原始指令、完整场景与候选裁剪图，模型只能返回匹配、明确不匹配或
不确定。两次新观测的肯定结果才报告语义完成；重复时间戳不计数。
当前采用至少 0.5 秒间隔、每个观察位置最多三次请求、每个物体默认 20 秒期限；这是待标定的
工程基线，不是 SG-Nav 的离散步数参数，也不是经过校准的概率保证。

原生 REACHED 和语义核验结果分别保留。断流、替换、换图、迟到回复、模型
错误和不支持图像的客户端不会伪报成功。看不清后可经原生预检主动换位置，
否定或观察耗尽后可选择当前场景里的其他候选，具体边界见下文。
不将两个时间点称为两个独立视角。
测试运行了真实 GoalService、LLMModule 和异步端口，替换了模型回复，因此
还不能证明真实图像的判断准确率。另修正了 RGBA 转换和 PIL 编码回退的红蓝
通道交换问题，避免颜色属性在送入模型前就已经错误。

1. **运行时验收**：任务身份和终态接线已完成本地验证；接下来用录制数据、
   原生 MuJoCo 和 S100P 无运动数据核对同一链路，不能把 Python 通过当作实机通过。
2. **观察点完善**：同层候选与原生路径预检已接入；下一步补足可视性、
   不同楼层/高度的原生地图候选和实测，不把几何可达等同于能看到目标。
3. **前沿输入**：从地图/探索的既有所有者提供有版本、坐标系、地面高度的
   候选；不在 Python 再维护一份竞争的实机代价图。
4. **核验扩展**：停靠核验、主动换位置和当前场景替代候选已接入；继续用
   录制数据、原生仿真与实机实测模型质量、位置选择及超时参数。
5. **语义记忆**：参考 3D-Mem 和 HOV-SG，先做可追溯、可失效的少量观测与
   地图地点关联，再评估复杂图结构，避免先引入整套模型框架。

上述运行时验收、可视性判断、前沿接线仍待完成。主动重观测还没有实机证据。S100P 没有 CUDA，模型推理必须
实测板端成本或采用现有外部推理端；离线失联时不能凭过期模型结果继续发新目标。
没有批准和测量前，不增加 GPU/Python 模型依赖，不整体复制上游 Habitat/ROS 运行时。

## 实机前的验证安排

### 2026-09-17：真实模型适配的本地闭环

核对官方当前接口后发现，现有默认 `kimi-k2.5` 已于 2026-08-31 下线。
`kimi-k2.6` 仍支持图像和非思考模式。依据
[模型列表](https://platform.kimi.com/docs/models) 和
[K2.6 接口说明](https://platform.kimi.com/docs/guide/kimi-k2-6-quickstart)，
未指定模型的 Moonshot 配置改用 K2.6 开放平台接口，禁用思考并省略 temperature。
显式模型配置仍保留；不把 Coding 套餐地址与开放平台默认配置混用。

这轮可复现的适配问题及修正：

| 问题 | 修正 |
| --- | --- |
| Moonshot 图像入口一律拒绝，`moonshot` 别名又拿不到默认配置 | 别名统一；为已核对协议的 K2.6 声明视觉能力，其他模型不假报支持 |
| 图像调用偷偷把 mini 模型换成更大的模型 | 单图、双图和文本共用请求实现，保留所选模型 |
| 图像入口把 reasoning 当成最终答案 | 只消费最终 content，缺失结果不能作为目标确认 |
| 超时异常文本为空，`LLMResponse.ok` 被判为真；一次超时立即熔断 | 错误至少含异常类型；超时按暂时性失败累计 |
| 延迟从回调完成后才计时，默认模型名为空 | 从请求派发用单调时钟计时，报告解析后的模型名 |
| 更换供应商继承旧地址、模型和密钥变量 | 同一供应商保留配置；不同供应商重新取默认值，显式覆盖仍生效 |
| 停止直接关闭事件循环，留下请求；换后端不关旧客户端 | 停止先取消请求并释放 SDK，切换时关闭旧客户端 |
| 温度错误耗尽重试后返回成功空串 | 无剩余重试时报告实际错误 |

`tests/decision/test_llm_vision_transport.py` 包含 18 个本地用例。
使用项目已声明的 OpenAI SDK（本次运行 3.14.1）和内存 HTTP transport，
覆盖实际请求 JSON、双图、流式回复、超时与取消。贯通用例经过真实
GoalService → SemanticPlannerModule → LLMModule → SDK，测试确认、否定、
三次不确定及 API 失败；原生执行端和 HTTP 回复由测试替代。

### 2026-09-17：有界的重新观察与替代候选

[SG-Nav 的重感知机制](https://arxiv.org/html/2410.08189v1) 在接近候选时
从多个观测累积可信度；在限定步数内不能确认时，放弃该候选并继续探索。
这里借鉴“候选可以被推翻、需要继续寻找”的结构，不移植它的离散动作或
把其可信度公式当成现场校准概率。

LingTu 的实现边界：

- 保留当前正在接近的物体；看到另一同类物体不会在接近过程中反复换目标。
  现有探索与视觉接管分支仍可工作。
- 一个物体最多尝试三个观察位置，每个位置最多请求三次模型。第一次
  停靠启动的默认 20 秒核验期限覆盖换位置过程，不重新续期。
- 新位置继续从同层环形候选中提出，由原生只读路径 RPC 决定是否可达。
  排除距已尝试位置、当前位置不足 0.30 m 的点，并请求 0.15 m 到达半径，
  避免普通大到达半径让“换位置”直接变成再次已到达。
- 移动期间不计入图像确认。原生 REACHED 后才接收新的同步观测，证据保留
  原生任务 ID、位置和观察位置编号。超时会取消在途原生任务，受理回执不当作停车证明。
- 明确不匹配或观察耗尽后，从当前新鲜场景中用完整原指令选择其他候选，
  排除本轮已尝试 ID。至多三个物体候选，不可达候选也计入上限；不确定
  不改写成明确不匹配。排除的是候选资格，物体及关系仍可作为场景参照，
  不删除参照物而破坏“旁边/附近”的约束。指令、地图或原生启动身份变化后清空这轮排除记录。
- 查询状态可见候选阶段及各物体核验证据；等待预检时不会只显示旧物体的
  不匹配状态。替代候选的忙碌预检具有独立定时器，断流后也能结束等待。
  取消、换图、重启或超时后，慢预检结果不得下发旧目标。

`tests/decision/test_semantic_reobservation.py` 使用真实语义模块、GoalService、
任务账本和线程，替换模型回复与原生端，覆盖换位置后确认、位置/调用预算、
替代候选、不可达候选、忙碌重试、拒绝/不明受理、移动超时取消及延迟结果失效。
补正了旧测试桩缺少回执必填字段的问题，并明确断言第一条目标确实被受理。
其中两个用例使用真实 GoalResolver，验证候选排除会生效，且被排除物体仍可参与关系评分。
本轮新增 24 项重观察用例。扩大的受影响回归 408 项通过，有一条既有 jieba
`pkg_resources` 弃用警告；补上断流时的预检超时处理后，最终针对性复测
136 项通过。修改文件通过 Ruff。

### 再读实现得到的迁移取舍

  还保留上一目标的选择惯性，并抑制重复的状态—动作组合。这支持“候选来自

## 2026-09-17 深度校验：观察候选的原生服务边界

原生导航已接入只读语义观察查询工作线程和类型化 DDS 请求/结果。工作线程从
ActiveOctomapGate 取得保存地图，复用 OctoPlanner 的支撑及净空判定生成指定高度层；
候选使用实际检查过的格心高度，缺少支撑的格不能连接候选路线。服务本身不发运动命令。

这轮确认并修复：

- 相机观察历史被当作位置黑名单，加上最小移动距离，导致狭小可达区域无法通过
  原地转向继续观察。新增测试在修复前复现 `candidates.empty()`，修复后要求连续
  多次转向都增加观察覆盖；覆盖历史仍按朝向和遮挡计算。

- 查询把 `covered_frontier_cells` 当作已知地图候选的可见格数，但已知地图分支
  将该字段置零。改用该分支的几何收益计数；它仍是采样估计，不是识别置信度。
- 工作线程完成到主循环取结果之间取消，原结果仍可能被返回。`poll()` 现在使
