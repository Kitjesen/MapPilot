LingTu runs LiDAR, SLAM, map services, planning and motion control as **native
C++ services over CycloneDDS, without a ROS runtime**. Python provides task
reasoning and external APIs; LingTu's Web console handles maps, goals and robot
status. ROS adapters are retained for explicit compatibility and replay only.

The shared workflow is **mapping → save/reload → localization → autonomous
navigation → safe stop**, with cancellation and manual takeover. Inspection
and semantic tasks build on the same navigation core.

Field qualification is in progress. [Product scope](docs/product.md) and the
[current roadmap](docs/roadmap.md#current-delivery-cycle) distinguish implemented
capabilities from verified results.

Factory inspection is **not yet accepted end to end**. The current
[sensor delivery ledger](docs/design/sensor-delivery-status.md) separates
implemented measurement/recording code, real-engine checks, unimplemented sensor
types, and the remaining same-Product Factory/navigation acceptance gates.

## Global planning results

![Global planning pipeline: source PCD to 3D occupancy map, native search and path diagnostics](docs/assets/planning/pipeline.svg)

Sample PCDs become a 3D occupancy map with occupied cells and modeled free layers
above support surfaces. Start/goal coordinates and robot geometry feed the
native 26-neighbor A* search, which checks body clearance, support and edge
sweep before accepting a connection. The returned path is checked and exported.

## Architecture

```text
LiDAR / IMU → native SLAM → saved map + localization
                                  ↓
Operator goal → OctoPlanner3D global route → SCAN local trajectory
             → navigation execution / recovery → motion arbitration → driver
```

C++ owns the field sensor, SLAM, map, planning and driver hot paths, communicating
through typed CycloneDDS. Python owns the Host, task reasoning and external APIs.
ProductControl owns Product lifecycle; native navigation owns final motion
arbitration. Perception and semantic tasks use these existing interfaces.
See [Architecture](docs/architecture.md) and [Runtime](docs/runtime.md).

The environments are `real` and `sim`; RobotConfig selects hardware, devices and
calibration. The [robot catalog](config/robots/README.md) contains `unitree/go2`
and `doso/thunder_v4`, with availability and validation recorded per environment.
Field releases target Linux/CycloneDDS. Simulation and physical robot tests
provide separate evidence.
