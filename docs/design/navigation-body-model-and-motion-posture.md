## 名称、行业来源与实现边界

**2026-10-26 命名决定：统一称“组合碰撞模型（Compound Collision Model）”。**
本文采用通用 compound collision 的表达，不新增品牌名、缩写、模块或文件格式。
该名称表示用多个简单碰撞形状及其相对变换共同表示机器人外形。盒、球、圆柱、
胶囊可以组合；URDF 是一种几何来源，MuJoCo 的实测部件也可以提供同类几何快照。

这不是灵途独创的机器人表示方法。2026-10-26 核对的上游资料如下；它们支持方法来源，
不证明灵途已经达到上游精度、速度或功能，也不代表本次引入了这些库或论文算法。

| 一手资料 | 已有做法 | 对灵途名称和边界的启示 |
|---|---|---|
| [Bullet `btCompoundShape`](https://github.com/bulletphysics/bullet3/blob/master/src/BulletCollision/CollisionShapes/btCompoundShape.h) | 一个复合形状保存多个子碰撞形状；`addChildShape()` 接收形状及局部变换，`updateChildTransform()` 更新子形状变换 | “多个形状＋相对变换”的组合表示是已有方法 |
| [MoveIt：URDF and SRDF](https://moveit.picknik.ai/main/doc/examples/urdf_srdf/urdf_srdf_tutorial.html#collision-checking) | 读取 URDF 的碰撞几何，区分显示几何与碰撞几何，并建议降低碰撞模型复杂度 | 使用 URDF collision 不是新算法；视觉模型与碰撞模型可以采用不同精度 |
| [FCL 官方 README](https://github.com/flexible-collision-library/fcl#readme) | 支持盒、球、胶囊、圆柱、凸体、mesh、octree，以及物体组的碰撞和距离查询 | 多原语检测与分组加速已有成熟实现；这里仅参考，不声明灵途调用了 FCL |
| [Drake：Geometry Queries and Roles](https://drake.mit.edu/doxygen_cxx/group__geometry__roles.html) | 同一物体可按显示、接触和距离查询等用途采用不同几何表示 | 物理接触和导航近似可以分工，但来源、坐标、覆盖及余量必须明确 |
| [Zimmermann 等，2022：Differentiable Collision Avoidance Using Collision Primitives](https://arxiv.org/abs/2204.09352) | 用简单碰撞原语近似复杂刚体，研究统一距离计算及其导数 | 原语近似早已有研究；灵途现有查询没有因此获得可微距离能力 |
| [Tracy、Howell、Manchester：Differentiable Collision Detection for a Set of Convex Primitives](https://arxiv.org/abs/2207.00669) | DCOL 用凸优化处理可组合凸原语的碰撞度量、接触及导数 | 属于另一个具体算法；灵途当前不是 DCOL 实现 |

### 各名称只表达一件事

| 名称 | 本项目中的含义 | 不能据此推断 |
|---|---|---|
| 组合碰撞模型 | 多个碰撞部件及相对变换构成的机体表示；旧文“URDF 分部模型”采用此称呼 | 不保证所有场景都优于单 OBB，不自动生成朝向或步态 |
| URDF | 机器人描述及 collision 几何的来源之一 | 配好显示 URDF 不等于正式导航选中了它 |
| `collision::Body` / `Part` | 现有 C++ 查询使用的模型容器与部件；OBB 和组合模型复用它 | 不是新增的产品、调度器或独立控制入口 |
| `BODY2` / `.body2` | 内部几何序列化标记与既有扩展名；记录原语、变换和支撑角色 | 不是算法名、行业标准或“第二代导航”；文件本身不包含在线 FK |
| 固定站姿快照 | 以一组已记录关节角导出的组合模型 | 不覆盖未来步态中的所有腿部位置 |
| 当前姿态/关节快照 | 依据实际测量更新的部件变换 | 不等于已经规划未来关节运动或落脚点 |
| 单 OBB | 以一个有向长方体近似机体的模型选择 | 不是组合模型的别名，不能自动代表所有附件与腿部范围 |

## 已定位的 L 形姿态问题

用户指出的是 `build/go2-envelope-20261025/corner-animation.mp4` 中 URDF 分部模型
约 50% 的姿态。原始输入是
`build/go2-envelope-20261025/results-final/corner_080/urdf_fixed_raw.json`。
这是合成三维地图中的原生全局规划结果回放，不是 Go2 步态、SCAN 执行或动力学录像。

2026-10-26 对原始路线的分析：

- 共 40 个位姿点，前 39 个点 yaw 均为 0；最后同一终点位置才转到 90°。
- 忽略两个小于 1 μm 的坐标舍入微段，有效平移 36 段、约 1.88284 m。
- 与机头方向接近 90° 的横移约 0.80000 m，占平移路程 42.49%。
- 50% 回放位置约为 `(0, 0.25493, 0.32023)`，yaw 仍为 0。
- 回放采用“平移长度＋0.25×转角”的归一化进度；50% 不是物理执行时间的一半。
- 最后的原地转身在回放进度约 82.74% 才开始。

分析数据：`build/go2-envelope-20261025/posture-review-20261026.json`。
其中 1 μm、85–95° 是识别数值微段和横移的离线分析口径，不是产品新门槛。

### 修改前的原因是朝向规划目标缺失，不是 URDF 无法转动

修改前的 `fixedHeadingGuide()`（现已改为
[`poseGuide()`](../../src/nav/cpp/planning/global/octoplanner/octoplanner3d_core.cpp)）
先用实际起点 yaw 检查一条 XYZ 候选。即使候选已经折弯，只要同一个 yaw 下身体
仍放得下，就把所有中间点写成这个 yaw，最后补终点朝向并返回。
只有这条候选失败，才进入完整的 `heading::search()`。

[`heading.cpp`](../../src/nav/cpp/planning/global/octoplanner/heading.cpp) 修改前的平移扩展
保持当前 heading、按欧氏距离计价；原地转向单独计价。
[`heading.hpp`](../../src/nav/cpp/planning/global/octoplanner/heading.hpp) 也明确说明转向
代价与路径切线无关。旧实现没有前向、侧向、后退运动的一致质量偏好。

因此更紧凑的分部模型让固定 yaw 的横移候选通过，而较大的 OBB 可能因角部碰撞
进入另一条搜索分支。**不能依靠更笨重的碰撞模型间接获得好看的转身。** 本次 URDF
约 90 ms 与 OBB 数秒的差异，也不是单纯的部件相交算法速度比较。

### 执行接口也必须一起处理

[`compilePoseRoute()`](../../src/nav/cpp/navigation/pose_route.cpp) 当前明确拒绝一条边
同时平移和改变 yaw。执行器把阶段 yaw 传给 SCAN 的 `bodyHeading` 和闭环控制，
不会自动把它改成路线切线。

`poseRouteBlend()` / `Executor::tryBlendPoseStage()` 现在可以为短的前向等高段及多个
相反曲率转角生成连续候选，不再要求 1.5 m 臂长或单 OBB。格点折线仅在实际栅格
分辨率允许的横向误差带内尝试弦线；所有新圆弧和连接仍以原分部 Body、逐点切向 yaw
完整扫掠。SCAN 检查优化后的样条；尚在入口且实测静止时可恢复原停转阶段，弯中失败
保留当前曲线和目标进行重规划。高差段和楼梯保持独立执行。

正确修复必须覆盖：候选选择的方向偏好、XYZ+yaw 表达、受支持的转弯连接、SCAN
跟踪与实际命令。只改搜索代价后输出当前执行器不支持的边，也不能算完成。

## 前向优先修改（首轮已完成基线）

该次修改改变朝向选择，不改变碰撞尺寸、地图证据或部署模型。
2026-10-26 的 S 弯复查后，当前按每段机体系位移计价：

```text
平移代价 = 三维长度 + w × (|侧向位移| + 2 × max(0, -前向位移))
转向代价 = 最短转角绝对值 / (2π / yaw_bins) × turn_cost_m
当前 w = 1.0，yaw_bins = 16，turn_cost_m = 0.10
```

在平地走同样的 1 m，前向、横移、后退的平移代价分别为 1、2、3。
30° 偏差增加 50%，45° 增加约 70.7%；这是连续软偏好，没有新增“偏差超过某角度便拒绝”的限制。
首版的 `水平长度 × (1-cos(delta))` 在 45° 时只增加约 29.3%，使 S 弯长直段
保持 45° 朝向比转正更便宜，已被当前按侧向距离计价取代。
原地转 90° 的代价为 0.4；因此短侧移与反复转身之间仍有合理取舍。
代价单位用于搜索比较，不是执行秒数。

修改到达三处：

1. 直达路线：起始 yaw、直达方向和目标 yaw 候选按同一总成本排序，不再优先返回
   列表里第一个可走的朝向。
2. 弯折 XYZ 候选：保留原始起点和目标 yaw，并从路线切线生成少量量化朝向；
   动态规划比较整条路线的转向与平移总成本，避免每遇到一个短 45° 网格段就来回转头。
   所有候选转向和移动仍经过三维机体扫掠，输出明确的先转后走阶段。
3. 完整 XYZ＋yaw 搜索：平移、转向和最后精确连接到目标的代价一致；第一个能连接
   终点的状态不再免费胜出，继续寻找更低代价的完整路线。耗尽迭代预算时保留
   已检查的完整路线，取消仍清空结果。

有限候选无解时继续原有完整姿态搜索。候选成功只说明在这条 XYZ 路线、有限朝向
集合中完成了优化，**不声称所有空间路线中的全局最优**。输出兼容 `compilePoseRoute()`，
但尚不能据此宣称 SCAN 物理跟踪或 Go2 实机已经通过。

### 首轮 S 弯代价修正与缓坡诊断（历史证据）

同一 S 弯的长直段为 `(0,0.20) → (0,0.95)`，长 0.75 m。首版保持 yaw=45°。
增加 45→90→45 的转向代价为 0.4，而旧偏角代价仅省约 0.21967，目标函数因此
主动选择了斜走。当前使用机体系侧向距离后，这一段可省约 0.53033，扣除转向
后仍更优约 0.13033；不需要无限增大权重或禁止侧移。

原生分部模型 7/7 回归确认长直段 yaw=90°，机体系侧向位移累计从约 0.63640 m
降为 0.10607 m，按路程加权平均偏角 12.79° → 2.13°。全部新增转向扫掠和执行
分段接口通过。但原地转向次数 2 → 4，输出仍是停转阶段，不能标成连续自然转弯。
新增 S 弯针对性测试先在旧实现失败，改后 heading/body smoke 与64组独立可达性
对照全部通过。17场景单次复查仍为14成功、3失败。

缓坡根因比“固定姿态不能爬坡”更具体：5 cm 体素顶面阶跃为 50 mm，而当前四足
接触容差总窗为35 mm，且要求完整足投影同一个水平面。另一个非接触小腿部件
`FL_calflower1` 在连续解析坡面上精确法向净空约14.768 mm，仍与占据体素相交。
这两项分别需要真实三维地面表面/接触查询和近地几何解释，单独加大gap不能修好。

独立解析平面与真实primitive的支持函数对照显示：同一固定关节水平Body在连续
坡面上可通过统一抬高约10.431～14.487 mm落入原竖直接触窗，并保持非接触部件
正净空。因此不能认定URDF或机器人本身走不了4.57°；现有±25mm/5mm步长微调
诊断也不足以否定这个窄区间。解析对照不是运行时地面证据，不能拿它清空体素。

该批次只有 OctoMap 查询，尚未接入原始表面窄相位；源码、红绿测试、原生路线、
回放和独立解析对照保留在[首轮记录](../../build/navigation-posture-terrain-20261026/README.md)。
它是后续修复的失败基线，不代表下文原始面与连续转弯适配后的状态。

### 与原生 SCAN 的差异及本轮误拒修复

[官方论文第 7 页](https://arxiv.org/pdf/2606.19555v1#page=7)确实报告了带障碍楼梯仿真，
以及 Go2 跨三层楼的 149 m、251 s 实机路线。其核心为三维位置 B-spline、给定的高度
参考和随 yaw 的双圆柱机身占据查询，闭环仍输出 `vx、vy、wz`，并未规划每只脚的落点。
因此不能把本地缓坡失败解释为“速度接口不支持”或“SCAN 本来不支持地形”。

固定站姿四足逐点必要接触、原固定高度制动外推及离散移动/转向阶段，均为 LingTu
增加的要求。上游没有要求四只冻结足在每个候选姿态都满足精确接触。下文已推进
短 S 弯和分部机体连续切向适配，但固定快照仍不能冒充未来步态。首轮 4.57° 失败
发生在全局 PlannerSession/BodyQuery，当时 SCAN 没有参与该失败请求。

另查出全局共享 `queryWorld()` 和 XYZ 顶点查询仍独立拒绝机体中心的 unknown 空气，
即使下方已有有效地面。本轮移除有地面支撑模式下的这项前置否决；保留实际占据
机体、地面缺失/unknown、已观测落差、边界及运动条件检查。不要求地面支撑的旧诊断
模式仍保留其顶点观测约定。这项改动不写入 free 体素，也不解除足部支撑规则，故不能
据此宣称上述缓坡或楼梯适配完成。

固定提交上游源码、调用链和剩余限制见[上游核查](../../build/scan-terrain-parity-20261026/upstream.md)、
[全局查询分析](../../build/scan-terrain-parity-20261026/global-findings.md)与
[执行分析](../../build/scan-terrain-parity-20261026/execution-findings.md)。本段记录实现范围，
不代替回归、接触物理或目标机运动验收。

原始查询中约32.47%的精确重复不足以靠结果复用单独解决实时性。

## 机体表示、关节姿态与运动朝向的区别

| 概念 | 决定什么 | 不决定什么 |
|---|---|---|
| 单 OBB | 一个随 yaw 转动的长方体占据范围 | 不自动决定沿哪条方向走，也不表达腿间空隙 |
| 组合碰撞模型 | 每个碰撞部件的位置、方向、形状和接触角色；URDF 可提供源几何 | 不自动决定前向优先、转角时机或足点 |
| 固定站姿组合模型快照 | 将一组固定关节角的 URDF collision 几何离线导出，现有文件标记为 BODY2 | 整体 XYZ/yaw 仍可变化；但腿没有随步态更新 |
| 实测关节 FK | 根据实际关节角计算各部件变换 | 不生成步态、不规划落脚点、不证明未来关节运动已被覆盖 |
| 路线 yaw / vx、vy、wz | 机头方向、前向/侧向速度与转向 | 不能代替真实碰撞与地面信息 |

正式底层仍接收速度命令。精确落脚控制是独立能力升级，当前不把它塞进本轮机体
表示修复。全局、局部和执行的区别是视野、时刻与所检查的运动不同，不是让几层
各自偷偷选择不同机器人形状。

没有证据表明 10 月 25 日那次清空路径，是在一次新的 Go2 分部模型实机失败后
作出的定量回退。历史上确实遇到支撑误拒、查询成本和执行衔接问题，但后来已有
相应修复；它们不能被概括成“URDF 太慢，所以不能用”。

这次冲突的具体原因是：

1. 两个聊天引用了不同时间的用户决定，部署采用较早的 OBB 选择，没有核对后续分部方向。
2. 旧文档不断在顶部追加段落，多个时期都写“当前”，同时出现 BODY2 和 OBB 的默认描述。
3. 模型文件选中、组件测试通过、正式运行、实机验收被混在一起描述。
4. “规划成功/耗时”没有同时评价身体朝向，使横移捷径看起来成了更优方案。

以上是决策与交接失配，不是 URDF 代码丢失。不能用“用户曾经选过 OBB”作为忽略
后续分部要求的理由，也不能未经新证据就再次把当前 Go2 默认切换回去并称已验收。

## 以后如何保持一致

- 本文记录用户要求和当前选择；RobotConfig/RunPlan 记录实际模型与参数；
  operations 记录真正部署的版本、改动理由和验证结果。三者作用不同。
- 改模型或改变转弯行为时，在同一次变更中更新上述对应位置，说明是目标改变、
  实现推进还是临时回退。实际回退需写出具体原因和恢复条件，不能只引用旧聊天。
- 实验结果进入 research/build 记录，主文只更新结论与证据入口；不再把连续多日
  的实验原文堆到“当前选择”之前。
- 发生来源冲突时，先核对最新用户指令和真实配置，再继续执行；不另建配置权威、
  自动评分框架、哈希登记或重复的审批流程。
