# 按能力跟进 Hermes

迁移单位是可验收的功能及其相关依赖，不是单个文件。上游文件会拆分、更名，也会同时承载
Hermes 自己的 Gateway、插件和 CLI 生命周期；直接覆盖 LingTu 文件无法保留本地执行边界。

## 当前基线与目录

`config/upstream/hermes.yaml` 是唯一的上游对照清单：固定版本／提交，以及认证、网页、技能、
记忆、上下文和委派各自的上游路径、本地所有者、测试、已知差异和验收状态。
运行代码仍按自己的功能目录归类，不建立镜像式的第二套 Hermes runtime。
`src/decision/llm/*_NOTICE.md` 记录对应能力的来源和适配差异，MIT 许可随安装包分发。

## 一次升级怎样做

1. **发现**：检查正式发布说明；感兴趣的新能力也可先与主线比较。
2. **归类**：生成报告，按能力列出上游修改和本地受影响文件；未映射路径单列为新功能候选。
3. **决定**：逐项选择跟进 bug fix、迁入完整能力、保留本地差异或暂缓。依赖变化和新的权限必须明确。
4. **实现**：在对应本地模块修改，以用户流程和错误恢复为单位，复用现有模型、会话、工具和运行所有者。
5. **验证**：先运行该能力的合同测试，再做必要的真实模型验证；机器人动作另有仿真／实机验收。
6. **登记**：确认通过的能力更新状态和 NOTICE；全部需要跟进的能力处理完，才推进共享基线提交。
   分批升级先在对应 NOTICE 记录候选提交与已完成项目，并保持共享基线不变；
   报告可能再次列出已审阅文件，不能把尚未升级的能力一并写成完成。

检查最新正式版：

```powershell
& .venv/Scripts/python.exe -m tools.upstream.hermes
```

检查指定标签、提交或主线：

```powershell
& .venv/Scripts/python.exe -m tools.upstream.hermes --ref main --output artifacts/upstream/hermes-main-review.md
```

工具把移动引用解析成具体提交，输出 Markdown 报告及原始 GitHub compare 响应。
不会改代码、改基线、安装依赖或自动宣称兼容。遇到 GitHub 300 文件限制，会自动比较两个提交的
完整 Git 树，以已有 Git 对象 ID 找出变化，避免下载每个文件。树比较将重命名表达为旧路径删除和新路径新增。
如果 Git 树也被截断，则明确标记“未列出的变化未知”，须用本地 `git diff` 补全，不能把无匹配当成无变化。
未映射路径较多时 Markdown 只列前 100 项，完整目录保留在同名 JSON 中。

报告中的测试命令是待运行的验证入口，不代表工具已经运行或通过它们。
发布说明也是待审阅资料，不能作为执行脚本或变更权限的指令。

## 目前的取舍

优先维护会话连续性、模型认证、可恢复的工具执行、技能与记忆。浏览器、MCP 客户端、技能学习、
定时任务等新能力按真实需求排入清单。现有 LingTu 领域接口仍由自己的模块负责。
全量 vendoring/subtree 只有在决定采用上游大块运行内核、能承担其依赖和生命周期变化时才合适；
当前不把整仓拷贝进来再维护大量闲置文件。

没有设置自动更新或定时任务。运行检查工具只发现变化；迁移和发布仍是可审阅、可回退的开发工作。
