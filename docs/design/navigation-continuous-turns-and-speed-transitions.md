## 原问题为什么没有随启动清理一起消失

启动清理修复了错误位置的朝向检查、竖向起伏导致的停稳误判等条件，
但未改变两项执行合同：路线编译器仍将普通拐角拆成局部终点和原地转向；
降低速度上限时仍丢弃超速旧样条，并等待从已停稳状态重新生成。
它们需要替换执行方式，单独删除判断会分别丢失朝向要求或破坏参考时序。

## 普通前向转弯

1. 兼容的前向移动段可以保留为一条有序三维参考线，中间角点不再是局部到达点。
2. 有适用条件时保留已有圆弧作为 SCAN 初始化参考；不适用时可以直接使用原始折线。
3. SCAN 负责优化、三维机体扫掠和候选轨迹检查；跟踪器按实际样条切线给出朝向。
4. 请求的终点 yaw 仍保留，终点附近的位置修正不能把机器人引向反方向。
5. 同一输入边可以同时平移和改变 yaw，但当前接口只接受首尾 yaw 均在任务容差内
   符合前进方向的采样位姿。任意独立 yaw、边走边横移或倒车的姿态调度没有加入。

真正要求原地旋转的阶段仍保留实测位置、水平停稳、角速度和三维旋转扫掠要求。
1 cm 转向中心条件只用于这些独立转向，不再成为兼容前向拐角的停车条件。
显式楼梯执行仍归原有楼梯模块管理，本文没有用通用切线路线替换它。

代码：`navigation/pose_route.*`、`navigation/executor.cpp`。
测试：`tests/nav/cpp/test_pose_route.cpp`。

历史 `benchmark_body_execution --keep-turn-stages` 依靠省略高度元数据强制停转；
当前原始折线可连续执行，这个参数已明确退休。旧对照应使用保留的历史二进制与记录，
不能继续输出一个实际上已经连续转弯的“停转版本”。

## 真正降低速度上限

0.5→0.3 m/s 是一个测试场景，不是 Product 的新默认速度。`nav` 和
`teleop_avoid` 延续每个机体轴 1 m/s 的现有约定。`compiler.py` 的正式 SCAN 编译链会
从解析后的 `path_follower_max_speed_mps` 继承规划上限，再按 Env、Product、会话
覆盖顺序生成最终参数。追查时 Python 参数表和 C++ 结构体曾保留通用 0.75 m/s
默认值，不能用来推断正式 RunPlan 或现场进程受该值限制。2026-10-28 已将普通
规划/控制及无配置入口的速度缺省统一为 1 m/s，并保留显式 Product/会话覆盖。
此前把默认值存在归因为
正式导航遗漏限速，证据不足；本说明予以修正。这段继承已存在于本轮修改前的
`HEAD`；本轮误加的两条 Product 重复声明已撤回，继续沿用原有继承机制。
轴限仍是 1 m/s，向量模长上限并不表示单轴变成 1.414 m/s。Product 参数及最终
RunPlan 环境变量都有回归。硬件部署和运行会话的参数需要另外核对。

异步命令积分回归覆盖 0.5→0.3 与 1.0→0.6 m/s。两组从明确给定的实测巡航
速度开始，专门检验运行中降速；它们不是从静止起步的加速性能测试。

```text
新限速输入
  → Task 优先处理最新输入、撤回尚未接管的旧候选
  → Backend 取得实测位置和水平速度
  → Manager 生成短三次样条减速过渡，完整检查带到达时间的三维扫掠
  → Follower 执行过渡
  → 普通 SCAN 从减速结束之后的未来边界生成并接管
```

旧样条整条速度界和实测水平速度均已符合新上限时，直接保留原样条和时钟。
旧样条不符合上限而机器人仍在移动时，显式过渡保留非零速度，避免先清空再停等。
机器人已静止或缺少有效实测运动状态时，仍从可用的实测状态正常规划。

过渡保留输入边界的位置、速度和参考加速度；水平速度来自实测，竖向导数来自旧参考，
避免把机身上下起伏误当作主动上升或下降指令。加速度和 jerk 的样条控制点界用于选定
时间间隔，末速度通过既有 `speedRatio()` 满足新巡航上限及固定朝向下的机体轴限。
初始参考加速度若为正，过渡开头可能短暂继续增速；不能声称速度每一时刻都单调下降。

`SplineTarget.speedTransitionEndS` 只标明这一条经检查的有限减速前缀。
普通优化器不获得“初速很大所以整条都放宽”的例外。后续 SCAN 接管边界的位置、
速度和加速度来自过渡样条，并且位于减速结束之后。

过渡使用普通物理秒、节点和起始时刻；没有单独慢放 Follower 时钟，也没有只修改
速度元数据来假装重定时，因此动态障碍仍按实际候选到达时间查询。

等待过渡时，旧超速样条 ID 失效并冻结参考，但输出从最后实际施加速度有界减速，
不因为一个正常降速输入立即输出零。过渡生成失败或求解迟到时仍可能减速至停止。
显式停止、占据障碍及最终实测/候选制动检查继续拥有原有优先级。

`upstream/plan_manage/{planner_manager,planner_fsm}.*`、`tracking/follower.cpp`。

## 本次证据应回答什么

- 前向转弯是否同时产生平移与转动，角点是否仍被当成到达点，终点 yaw 是否保留。
- 实测运动中的降速是否产生经检查的新过渡，原样条是否可能复活。
- 减速过渡及后续 SCAN 边界的 P/V/A 是否一致，命令每帧变化是否满足加速度界。
- 同一条行人横穿几何在不同到达时刻是否分别得到接受和拒绝。
- 连续降低上限、取消、冻结和真实阻挡是否仍得到正确结果。
- 从命令积分出来的实际位置与接管参考相差多少，不能把计划位置直接当成跟踪结果。

## 尚不能据此声称什么

- 当前优化器没有在每次迭代内部响应 Task 的取消请求；新输入能够使陈旧结果失效，
  但正在进行的求解仍可能延迟下一条过渡生成。
- P/V/A 的解析边界对应 Backend 收到的快照。异步验证、接收和真实机器人响应会产生
  状态老化误差；命令积分测试应记录该误差，物理和现场验证仍需单独完成。
- 当前没有任意独立 XYZ+yaw 的联合轨迹优化，也没有新增落脚点控制或部署到机器人。
