## 2026-10-25：恢复实时局部障碍查询的未知准入

OBB 局部查询恢复为在有效滚动网格范围内检查实测三维障碍，不再要求整个机身和制动
扫掠体积都逐格 known-free。雷达自身遮挡造成的未观测空气因此不再单独阻止起步。
这会改变此前局部“遇到未知必拒绝”的准入策略，并不证明所有新扫掠空间都已观测为空。
原始 occupied、known-free 和 unknown 位图不改写；显式支撑的观测要求、网格覆盖
范围、动态预测、三维扫掠和实测障碍制动检查保留。随后全局策略也已调整，见本页首节。

## 2026-10-24 设计选择：RobotConfig 选定分部模型，保留 OBB 回退

森哥在 2026-10-24 将方向调整为：**由 RobotConfig 选择离线导出的 BODY2 分部模型；没有已核对分部模型的机器人继续使用尺寸生成的 OBB**。BODY2 来自 URDF 的 collision primitive 和固定关节姿态，原生端只读取已经导出的几何，不在规划热路径解析 URDF/XML 或 visual mesh，也不执行在线关节 FK。当前工作树的主组合仍为 OctoPlanner3D + SCAN；正式端点的配置、模型加载和目标请求接线已经完成，当前证据是配置回归、原生组件和合成地图，尚未完成完整 Product/DDS/目标板或真实机器狗运动验收。其他受支持机器人继续从各自 RobotConfig 选择模型或 OBB 回退，不硬编码 Go2。

该轮 Go2 的 `config/robots/unitree/go2/robot.yaml` 选择
`body/go2_mid360_flatpack.body2`。该文件保留安装版 URDF 的 34 个 collision
primitive，并把四个足部球体标为显式支撑接触部件。它是固定标称站姿的几何输入，
不代表完整步态包络，也不代表 D435i 或支架已经被模型覆盖。Thunder V4 当前没有
仓库内可核对的 URDF collision 文件，仍使用 RobotConfig 尺寸 OBB，不能假称已经
完成 Thunder 的 URDF 接入。

`buildNavigationBody()` 使用现有 `vehicle_length_m`、`vehicle_width_m` 和水平硬余量，分别得到 `halfX = length/2 + margin`、`halfY = width/2 + margin`。Z 范围直接取现有 `[-collision_clearance_below_m, +collision_clearance_above_m]`。余量已经写入水平尺寸，`Body.margin_m = 0`，不重复膨胀，也不给上下净空额外加水平余量。

Go2 当前配置的标称长度 0.76 m、宽度 0.31 m、水平硬余量 0.10 m，对应 **0.96 × 0.51 m、Z ∈ [-0.10, +0.24] m** 的导航盒体。它是固定步态的导航障碍包络假设，不等于已实测覆盖腿部、附件和所有姿态；实机仍须测量确认。该默认查询保留三维体积、占据、自由/未知空间、支撑和高度约束，但只显式搜索/执行 yaw，**不等于完整六自由度 roll/pitch 姿态规划**。

主链路共享同一份不可变 Body：全局请求及 XYZ+yaw 搜索 → Route/Executor → SCAN 局部候选 → Recovery → 原生最终指令仲裁。正式碰撞输入已经提供 raw measured occupied 与 known-free 存储；分部模型直接检查原始三维体素，不能用旧圆柱膨胀图再次膨胀，也不能用缺失的原始证据放行。全局路线的稳定移动段/原地转向进入既有姿态执行接口；普通 XYZ 输入则由选中的路线引导段给出显式 `bodyHeading`，SCAN 与 Follower 消费同一朝向，局部验证覆盖实际 yaw 到该朝向的转动及运动扫掠。

上面列出的检查不是六套新算法，也不是每个候选都启动一套独立系统：全局只在
规划时检查候选 Body 和路线边，SCAN 只负责执行期间的局部候选，Executor 负责
当前状态和制动的最后一道判断。为了让产品容易维护，不保存每个路线段的一串
版本号；地图或 Body 变化时直接取消旧路线并重新规划。

动态障碍继续参与 Body 路径和制动查询。当前预测竖直圆柱用保守 AABB 表示，与同一 Body 部件做相交检查；检查按对应到达时间插值，包含障碍预测时域终点、原地等待、平移和转动。这个外接 AABB 可能比圆柱更早拒绝角部净空，不能声称精确圆柱窄阶段；没有为了 OBB 关闭动态避障。

| 可选组合 | 当前几何合同 |
| --- | --- |
| OctoPlanner3D + SCAN | 全局带朝向 OBB、局部/恢复/最终仲裁共享同一 Body；本轮主验收对象 |
| FAR + SCAN | FAR 保留现有 XYZ 全局候选，不宣称全局朝向 OBB 验证；SCAN 局部、恢复和最终仲裁使用配置 OBB |
| OctoPlanner3D 或 FAR + CMU | 保留既有 XYZ/CMU 兼容路径，配置 Body 为空；不把它标为本轮统一 OBB 链路 |

楼梯仍沿用现有模式切换、梯段朝向、限速、退出恢复与取消流程。Traversing 期间由楼梯轴朝向指导局部重规划，同一 OBB 重新验证实际姿态到梯段朝向及局部运动；退出后恢复原姿态段要求。落在楼梯上的显式最终 yaw 若与梯段朝向冲突，不报告到达。几何余量与到达容差分离：零 Body margin 仍保留 1 cm 中间段位置容差；只有显式实测关节快照才启用有界的 2 cm 高度浮动容差，固定默认 OBB 不冒充关节观测。14 项姿态路线回归通过只证明本地原生合同，不是楼梯物理或实机验收。

### 首轮统一 OBB 证据（2026-10-23）

- 当前原生组件回归：Executor 116 项、SCAN Body 12 项、SCAN planner 101 项、姿态路线 14 项及 Recovery sequence 16 项通过。最终碰撞取证专项 2 项也通过。Executor 的显式 Route Body 覆盖用例已推进外部执行时钟并确认实际正速度；构建和原始结果见证据目录。
- 单 OBB 30 m 直线组件执行 53.08 s 到达；同一双墙场景两次运行分别 56.20 / 56.45 s 到达。三次均无 OBB 占据命中、无效查询或最终几何制动限速/停车；组件取消后的下一拍为零。速度上限 0.6 m/s、加速度 2.0 m/s² 未改变。双墙最新平均命令速度 0.549 m/s、峰值 0.597 m/s，仍有转弯速度波动。
- 收尾保留并行的轨迹衔接修改后重新构建，`integrated` 当前组合直线 55.15 s、双墙 59.18 s 到达，命中/无效查询/最终几何制动触发仍为零。双墙平均/峰值为 0.542/0.600 m/s，全局冷请求 2.325 s。这是更新后的组合，不能把上条较快的时间当成当前组合时延，也不能称为同一二进制的第三次重复。
- 首版全朝向搜索在同一绕障场景超过 300 s。现在先复用现有三维 XYZ 搜索提出固定朝向候选，再以原 OBB/支撑查询核验每点、每段、原始起终点接入及末端转身；不通过时继续朝向搜索。候选与后续搜索共享原有总展开预算，不新增开关或二维授权图。最新冷请求直线 0.170 s、双墙 2.380 s；这是本机 Windows Release 用时，不代表 NX 性能。
- 历史双圆柱双墙运行 53.81 s、2 拍包络占据命中；新运行没有命中但略慢。新运行还加入最终几何制动，因此这是整条组件链的结果对照，不是只改变形状的单变量实验，更不是实机接触对照。
- 证据与原始日志：[本轮报告](../../../build/obb-unification-20261023/README.md)。不把历史 URDF/Thunder 物理结果移作新 OBB 的端到端证据。碰撞诊断取证也按实际 Body 范围收集，避免沿用旧圆柱裁掉盒体角部证据；该采集范围不参与运动授权。

上述组件使用理想反馈及合成地图/观测的边界必须随结果保留。Linux/目标板时延、完整 Product/DDS/driver 闭环、Go2 实测步态包络、坡面 roll/pitch、楼梯物理执行和监督现场运动均仍需各自证据。

当前代码入口：`endpoint/nav/app/config/build.cpp` 的 `buildNavigationBody/buildExecutorConfig`；`endpoint/nav/app/goal/plan.cpp`、`goal/task.cpp`、`app/loop.cpp` 和 `endpoint/nav/main.cpp` 的目标/路线/最终仲裁接线；`navigation/executor.cpp`、`navigation/recovery.cpp` 和 `planning/local/scan/grid.cpp` 的共同 Body 消费。以下旧实验保留原始数据和当时结论，不再作为当前默认接入计划。

### 历史组件执行接入与当时范围

当时保留 XYZ 参考路线＋SCAN 作为正式基础，只在需要独立朝向的固定场景验证姿态路线；该采用范围已由本页开头的 2026-10-23 单 OBB 决定更新。历史 0.44 m 基线的 33.51% 缩短不能当成当前产品收益。

第一期采用显式姿态路线和稳定平移段/原地转身。实际接口保留旧 XYZ 输入，在 `Route` 中新增 `posePoints` 与共享 `body`；新姿态点定义为：

```cpp
struct PoseRoutePoint {
  nav_kernel::Vec3 position;
  double yaw;
};
```

位置与朝向存在同一个点中。旧 `Route.points` 沿用原有执行语义；姿态路线逐点保留 map 系 yaw。Route 的终态容差与速度仍生效；早期实现曾拒绝姿态路线与楼梯组合，该限制已在本轮按上述楼梯合同修正，仍不能由本地测试推断楼梯物理可执行。全局路线没有时间戳，SCAN 决定局部速度与时间参数。

当前heading搜索恰好分别生成“位置改变、yaw不变”和“位置不变、yaw改变”的边，因此接收路线时可以一次性分出连续同朝向的移动范围及转身边：

1. 移动范围的参考和bodyHeading保持稳定，交给SCAN；局部查询与follower消费同一朝向。局部horizon不能跨过尚未完成的转身要求。
2. 到转身位置后停止平移，复用Executor已有的朝向控制和最终运动检查。以实际位置/朝向/运动状态确认完成；转动扫掠从实际姿态重新核验，不把计划到达当作真实到达。
3. 完成后才换到下一移动范围并更新一次参考；不把每个格点建成任务，不每tick更换bodyHeading触发候选反复失效。任务ID、取消、地图切换及恢复继续由现有Executor和任务归属处理。
4. 同XYZ、不同yaw的点不得被空间去重删除。map系yaw到planning frame沿用现有楼梯变换规则。
5. 第一阶段若输入某段要求同时平移和连续转动，而当前执行器不支持，应明确拒绝该段；不能静默改成先转后走，因为两者扫掠不同。当前原生demo不需要这种同步边。

模型接入与上述路线接口一起验证：Mapd仍维护实时地图，分部查询使用未按旧双圆柱膨胀的原始三维占据，避免双重膨胀；全局、局部候选及最终运动检查使用同源安装模型。动态腿部范围、相机附件与足底接触语义不由当前标称站姿替代。

三维地形另有明确边界：现有SCAN继承上游Projected XY搜索、线性Z参考和零Z优化梯度。局部XY可以离开原全局路径，最终候选仍需符合三维支撑/通路条件；不通过直接解锁Z使机器人绕进空中。第一期姿态执行先验收平地窄门/拐角，再用阶梯、平台和多层用例验证高度剖面与底层步态。

验收保留三个正例与0.28 m、转动中间碰墙、起点占据、支撑断口等负例；比较当前XYZ方案与姿态方案在同一物理机体上的到达、碰撞、实际路线、yaw/横向/Z误差、等待次数及耗时。先验证同一移动范围连续控制不重启规划、段间旧候选不复活，再接MuJoCo物理反馈。当前12.7 s全局搜索需要单独分析扩展数与几何查询耗时，16个yaw候选不等于固定16倍耗时。

### 2026-10-23 历史实验：轮足支撑与实时关节快照

`Part` 保留 Box/Sphere/Cylinder/Capsule、原始半径/半长度、link变换，以及显式的 `support_contact` 与 `support_required`。前者允许底部支撑接触，后者表示当前姿态必须获得支撑；摆动足可以不要求当下承载，但其侧向障碍检查仍完整保留。`BODY2` 文件保存这些字段，历史 count-first OBB 文件仍可复现。

圆柱采用圆柱轴和重力投影构建规范 OBB，消除轮子绕自身轴自转造成的假最低点。无余量的圆柱最低点与原始圆柱一致；球体采用精确球/AABB查询。圆柱和胶囊其余方向仍为保守 OBB，不声称完整 mesh 窄阶段。普通障碍保留原碰撞余量。

全局与 SCAN 共用 `collision/support.hpp`：在原型最低点附近寻找同一高度的局部占据上表面，逐柱要求上方已知自由；同 XY 的不同层面分别处理。当前受测平地容差为最多5mm接触穿入、30mm支撑间隙。它不将未知地面补齐，也不等于真实多足稳定性判断。只证明原型与实际余量覆盖的投影，删除了会额外要求一整格侧向净空的错误扩张；贴墙3cm净空的回归由失败变为通过，真正切墙与支撑坑洞仍拒绝，未知证据不能补齐必需的支撑。

支撑许可只覆盖已证明 patch 内、不高于其表面的地面体素。原型深穿地、腿/机身/传感器撞地、足侧墙和台阶立面仍拒绝。细体素下，余量碰到的地面更深层可共享同一许可；未知体素不提供支撑许可，全局未知碰撞查询仍保留。

`LocalPlanRequest.observedBody` 与 `ExecutionObservation.body_geometry` 携带实际关节和机身姿态快照，旋转/俯仰烘入 yaw-relative 部件变换。稳定 `body` 仍作为模型/任务身份，逐帧关节更新不会重启整条路线。SCAN查询与组件最终检查使用当前快照；异步候选不能替代最后的实际机体/制动检查。单条预测扫掠仍固定这次关节快照，不是未来完整步态预测。

真实步态测试进一步暴露了中间段 Z 门槛与到达稳定性问题：实际机身 heave 约9mm，不能通过水平速度命令消除。当时完整实测机体快照采用 `min(配置高度容差, 模型余量)`，本次为20mm、XY转向中心为5mm；当前默认零余量 OBB 已将几何余量与到达容差分离，具体规则以上方当前章节为准。转身仍按实际位置完整扫掠。终点仍须每帧在任务位置/朝向范围内；半秒内实际三维位置与 yaw 保持有界才报告成功，持续水平/垂直漂移及旧观测不能通过。原无快照路径保留瞬时速度判断。最终朝向先进入容差内部再保持稳定观察，任务最终误差范围不变。

本轮证据采用 Thunder V4 自身模型与既有 policy_4998，实际 MuJoCo 动力学，不移动基座伪造反馈。Go2仍仅有本仓库的固定模型/运动学用例。没有安装新依赖、启动实机或启用 Product 默认新模型。

## 2026-10-23：制动查询的重复计算优化

`Grid::brakingOccupancy` 保留实际速度与拟下发速度两条调用，分别验证已有运动和新命令。预测停止时间不等于计算耗时；应分别记录每帧查询时间、整轮累计查询时间和机器人执行时间。

本次只在一次不可变 Grid/机体快照内复用相邻段共用端点：上一段末端已经通过的 margin 不小于本段要求时，无需再次查询这个起点；margin 增大则重查，不加 epsilon 放宽。对支撑部件，缩小 margin 后的支撑列集合是原集合的子集，原支撑层仍有效；碰撞体和待查体素也只会缩小。每段末端仍独立检查，不跨帧缓存地图或关节结果。

没有动态预测、且全部部件都无 `support_contact`/`support_required` 时，按有效制动时间均匀采样同一条圆弧。包络点速上界 `B = |v_xy| + R * |wz|`，每段两端使用 `B * Δτ / 2` 的余量覆盖段间运动；点位移间隔不大于 `min(0.01 m, 0.25 * resolution)`，每段角度不大于0.05 rad。空间余量最多5mm，完整累计转角不取最短角，整圈旋转仍检查中间姿态。新旧保守采样的位置不同，不承诺所有贴边输入的返回值完全相同。

存在动态障碍或轮足接触语义时，保留原实际时间采样；动态障碍仍按对应到达时间判断，轮足支撑的采样位置不变。未知空间、支撑缺口、真实占据和最终运动仲裁的职责不变。此优化没有补齐单OBB的腿部包络、坡面姿态或正式Product物理执行资格。

固定输入测速入口为 `tests/nav/cpp/benchmark_scan_braking.cpp`，支持单OBB尺寸夹具和 `--body` 读取真实BODY2部件。前后可执行文件、三组交替测速、相同6m物理任务和报告集中保存在 `build/braking-cost-20261023/`。34项局部机体/支撑回归包含中段障碍、未知、多圈旋转、弧线角点、动态横穿、近地净空和支撑缺口；实机表现仍需目标平台验证。
