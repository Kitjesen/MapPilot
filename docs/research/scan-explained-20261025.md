# 读懂 SCAN：从函数目录到导航系统

这份说明解释函数清单的含义，以及如何用当前代码理解规划、优化和闭环控制。
它不以函数数量衡量完成度，也不把编译、组件测试和实际运动混为同一种证据。

## 先看那几个数字

修复前清单记录25个源文件/头文件、276个函数体、5个显式defaulted、6个显式deleted，
以及168条非定义声明。它描述代码的组织形式，不是276项机器人能力。

```cpp
double meanSpeed();                    // 声明：告诉编译器有这个函数。
double meanSpeed() { return 0.6; }     // 定义：给出真正执行的代码。
Planner() = default;                  // 让编译器生成默认构造行为。
Planner(const Planner&) = delete;     // 禁止复制这个对象。
```

同一函数通常在头文件声明，在cpp实现；这两处不能算成两个功能。`= delete`不表示
源码丢失或算法没做，而是明确禁止操作。例如持有工作线程的对象不能随便复制。
`= default`也不是额外算法，只是采用语言提供的默认行为。

一个getter可能只有一行，`reboundReplan()`却组织整段轨迹生成。它们都算一个函数，
所以数量不代表复杂度、速度、质量或产品成熟度。修复中删除9个无定义旧声明，会让
目录变短，却不会减少现有实际能力。

## Clang 是什么

Clang是C/C++编译器工具链的一部分。它先读懂程序，再把程序交给后续编译阶段。
本轮目录工具用它读取语法树，没有改变产品原来的MSVC/GCC构建选择。

```text
C++源码
  → 词法/语法分析
  → 抽象语法树 AST：类、函数、参数、表达式、作用域
  → 类型与语义检查
  → 后续编译、优化和机器代码
```

目录脚本借用AST，准确区分`Grid::resolution()`和其他类的同名方法，识别重载、
构造、析构和inline；简单搜索“名字后面有括号”还会误把函数调用当成定义。

Clang能指出漏return、类型不匹配等问题，也能给出函数的语义身份。它不会因为
`applyLinearZReference()`语法正确，就知道机器人应当保留坡顶。那是算法契约问题。
AST也不是运行日志：它能看到函数存在，不能直接证明产品何时调用它。

## 从一次任务看各层职责

假设机器人需要沿一条先升高、再回到原高度的通道前进：

```text
全局参考路线：位置、朝向和中间高程
  → Executor选择本轮任务/路线阶段
  → Task/Backend持有输入、安排求解并转换接口
  → FSM确定当前状态、局部目标及对应参考区间
  → PlannerManager形成满足边界的初始轨迹
  → BsplineOptimizer调整局部样条，L-BFGS负责数值迭代
  → UniformBspline表示并计算位置、速度和加速度
  → Follower/闭环控制器根据实际状态计算速度命令
  → 最终运动仲裁进行实时几何/制动判断
  → Driver转发检查后的速度给底层控制器
```

Grid/GridMap贯穿求解和检查过程，回答三维地图查询；它不是管道末端另一个规划器。
PolynomialTraj负责初始多项式和求值；getMeanVel只属于统计，不控制上述任务。

| 模块 | 输入 | 输出 | 本层不能独自证明什么 |
|---|---|---|---|
| Task/Backend | 请求、地图快照、机器人状态 | 排队/求解结果与诊断 | 线程在运行不等于轨迹可执行 |
| FSM | 目标、里程计、执行反馈 | 何时规划、跟踪、等待或停止 | 进入EXEC不等于机器人到达 |
| Manager | 局部起终状态、参考区间 | 初始/重定时后的轨迹 | 初始轨迹不一定避障或满足速度限制 |
| A* | 起终位置、占据查询 | 局部避障引导 | 离散引导不是最终B-spline |
| 优化器 | 控制点、参考和代价参数 | 优化控制点及成功/失败 | 数值收敛不等于物理可走 |
| Grid | 形状、位姿/扫掠、三维证据 | 自由/占据/未知及支撑判断 | 机体有净空不等于步态稳定 |
| 跟踪控制器 | 期望样条、实际位姿/速度 | 速度命令 | 参考走完不等于实际到达 |

正式成功还要检查实际三维位置、朝向、实测速度及持续静止条件。

## 更深入的第一课：路线与轨迹不同

一条路线可以写成`p(s)`：s表示沿路走到哪里。轨迹是`p(t)`：t表示哪一秒。
同样的几何路线，走3秒或10秒，碰撞几何可能相同，但速度、加速度和制动不同。

`v(t)=dp/dt`，`a(t)=d²p/dt²`，`jerk(t)=d³p/dt³`。
若保持几何、把时间整体放大k倍，速度变为1/k，加速度1/k²，jerk变为1/k³。

这解释了为什么“重定时”能让过快的轨迹满足导数限制。但机器人已经在移动时，
它的实际起始速度不能被数学上随便除以k；所以现有代码对移动边界要保持物理P/V/A
并重新拟合，而不是盲目缩放。P/V/A分别是位置、速度、加速度。

新轨迹接管旧轨迹时，也要看接管时刻的位置、速度、加速度是否连续。仅两条线
画在一起接上了，不代表运动命令没有跳变。

## 更深入的第二课：代价与约束不同

优化器大致求解：

`min J = λ平滑·J平滑 + λ避障·J避障 + λ参考·J拟合 + λ运动·J运动`

λ表示各目标的权重。把避障代价权重调高，只是使求解器更不愿接近障碍；不能因此
保证一定无碰撞。非凸问题可能有局部解，也可能求解失败。

最终三维碰撞/扫掠与导数验收回答的是“候选是否满足准入条件”。它与“候选的代价
较小”不同。修复Refine时保留这些验收，并让控制点来自求解器真实返回的解，
避免拿最后一次失败试探的缓存冒充求解结果。

jerk作为平滑代价也不等于每时刻严格限制jerk；采样最大速度也不等于解析速度上界。
论文和产品界面都应按真实测量方法命名结果。

## 更深入的第三课：搜索的数据结构会改变算法行为

A*常用`f=g+h`排序：g是已经走过的代价，h是对剩余代价的估计。优先队列必须
按入队优先级保持正确顺序。若队里节点分数从30降到1，却不调整堆，队头可能还是10。

本轮修复在队列条目里保存入队分数，发现更好的路径就加入新条目，弹出时跳过过期
条目。这是搜索状态维护，不是新增规划层。测试应比较真实搜索路线与独立图论下界，
不能复制同一份A*再彼此对比后就宣布正确。

局部DynAStar的Z由起终插值，主要提供避障引导；它与正式全局OctoPlanner3D的
XYZ/yaw搜索不是同一个算法。两者的耗时和能力必须分别讨论。

## 更深入的第四课：三维数据不能在中间被悄悄降维

```text
原参考：0.5 m → 1.1 m → 0.5 m
旧种子：0.5 m → 0.5 m → 0.5 m
```

只保留起终点，无法区分平地和经过坡顶的路线。修复把当前参考区间传给Manager，
按三维进度保留中间几何，继续使用原有时间种子与端点边界；最终轨迹仍接受完整查询。
它不是将优化器改成可以任意飞行，也不是给底层新增落脚控制。

同一XY可能同时有楼上、楼下表面，因此不能简单使用单值`z=f(x,y)`替代这里的
路线进度和三维证据。导航必须知道自己沿哪一条连续参考前进。

## 更深入的第五课：怎样知道结果可信

| 问题 | 适合的方法/工具 | 能得到的证据 |
|---|---|---|
| 漏return、类型与函数目录 | GCC/MSVC告警、Clang AST | 编译/语法层证据 |
| 统计公式是否正确 | 单项式、交叉项解析积分，确定采样时刻 | 数学对照，不依赖同一实现 |
| 搜索是否按预期找路 | 独立图论下界、Dijkstra或正确参考队列 | 固定离散图上的路线代价与扩展行为 |
| 优化梯度是否正确 | 有限差分与解析梯度比较 | 成本/梯度局部一致性；不证明全局最优 |
| 新旧轨迹接管是否连续 | 在同一物理时刻比较P/V/A | 接管边界，而非只比较动画 |
| 失败能否复现 | 保存真实Body、三维证据、支撑、预测时序并重放 | 同输入是否得到同判断 |
| 当前控制器是否能通过 | 原生物理闭环、实际接触和运动记录 | 所选机器人/控制器/场景的能力 |
| 现场平台是否能执行 | 目标架构构建、无运动就绪、监督运动 | 对应硬件的分级现场证据 |

这些方法分别回答不同问题。Clang不能代替物理，物理一次成功也不能证明所有输入。
本轮运行过的检查与尚未运行的方法会在修复记录中明确区分。

## 推荐的阅读顺序

先读Task/Backend和FSM，理解输入、状态和结果；再读Manager，跟踪一条请求的实际
轨迹生成；接着读UniformBspline和Optimizer，理解变量、时间与代价；最后沿Grid和
最终控制查询核对验收。L-BFGS的线搜索与曲率更新适合在这之后阅读。

对每个函数，先回答“调用者给它什么、调用者拿结果做什么”，再研究内部公式。
这比记住几百个函数名更接近真正理解系统。
