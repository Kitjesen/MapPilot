# 轻量模式切换：官方参考与实施顺序

日期：2026-11-08，更新于 2026-11-09。状态：局部算法切换、建图档案跨重启恢复与独立 SLAM 模式切换已实现并完成本地验证；完整 Product 建图/导航服务热切尚未实现。恢复实现与证据见 [建图档案恢复](mapping-restore-20261109.md)。

## 建议

森哥确认：单独保存后仍可继续建图；从建图切到导航时，切换流程必须先保存当前成果，再自动完成所需后台处理，成功后才进入导航。这两种操作分别保留，不能要求用户先手动准备旧保存版本再切换。后续同图服务热切需要保留建图上下文，切回时恢复原图续建。

模式切换目标是“同一机器人、同一环境，按需在建图和导航间切换，尽量保留采集与定位服务”。允许机器人在交接时停住；不承诺持续运动中无缝切换。复用 ProductControl，不增加第二个模式管理器，不引入 ROS 或插件框架。

轻量化首先减少重复初始化、地图读盘和索引重建。进程常驻本身不保证 CPU/RAM 更低：闲置算法应停止计算，重型后端按需创建。控制频率热更新单独处理，不作为第一阶段目标。

### 继续建图、重新定位与 ROS 2 的对照

2026-11-08 补充：ROS 2 本身没有统一的“继续建图”开关，能力属于具体 SLAM 包。

- [RTAB-Map 官方说明，固定提交 2a411a8](https://github.com/introlab/rtabmap_ros/blob/2a411a8dfe15c88c5c8694cdfd8bfaa1dcea683a/rtabmap_slam/README.md#mapping-and-localization)：两项 mode 服务支持运行时切换。官方同时说明，切回 mapping 会开始新的建图段，依靠回环建立它与原图的联系。不能只看到封装回调修改一个参数，就断言内部不需要重新关联。
- [slam_toolbox 官方说明，固定提交 7376b23](https://github.com/SteveMacenski/slam_toolbox/blob/7376b23689d47d0be2a1dd0c58f5eb7085ac8a55/README.md#lifelong-mapping)：支持保存/加载位姿图与扫描等数据后继续建图，重新初始化时需要将当前扫描与地图对应。`serialize_map` 用于保存可续建资料，`save_map` 的导航地图图像不能替代它。它是二维参考实现，非 LingTu 三维算法替换方案。
- [Nav2 官方边建图边导航教程](https://docs.nav2.org/lyrical/tutorials/general_tutorials/navigation2_with_slam/navigation2_with_slam/)：SLAM 发布地图和 map→odom，Nav2 可以同时导航。地图是否继续更新与机器人是否执行导航是两个不同决策。

因此调整产品解释：

1. “继续建图”描述用户意图，不要求用户理解进程或先手动执行重定位，也不必增加为第三种互斥模式。界面可用“建图/更新当前地图”表达。
2. 同一地图定位仍有效且原建图上下文可用时，复用当前位姿并核验新扫描与旧图的关系，恢复追加；不应仅因模式切换强制做无初值全局搜索。
3. 定位失效、重启或机器人被搬动后，需要重新确认当前位置。可用初值做局部匹配，否则使用全局重定位；匹配成功后再将新观测加入旧图。
4. 恢复当前位置与恢复原建图图是两件事。2026-11-09 已补齐新格式档案的读取、原在线图恢复和匹配后续建，并接入 ProductControl 冷启动；见上方实施记录。只有成品 PCD/OctoMap 不能被当作完整图恢复。
5. 本计划先做同进程热切，是第一版范围，不是产品永久禁止跨重启续建。跨重启续建要在建图档案恢复完成后单独验收。

用户要求“离开建图、进入正式导航前先保存并处理当前成果”继续保留。这是当前产品流程要求，不是 ROS 2 或 SLAM 算法的普遍限制。Nav2 的二维在线导航示例也不证明 LingTu 的 OctoPlanner3D 已支持任意实时地图更新。

## 2026-11-08：建图与导航热切的实施设计

本节是当前源码核对后的实施方案，没有将产品声明改为支持热切，也没有修改运行代码。第一版支持同一 robot/env、设备标定不变、同一份保留中的建图历史与其保存地图之间的 `map ↔ nav`。覆盖 standard，以及两边相机配置一致的 camera 变体；semantic 等模块图不同的变体保持现有切换能力，另行适配。

### 操作语义

- 保存地图仍独立：原始成果落盘后，默认自动后台处理；仍可继续建图，不自动进入导航。
- 从建图切导航必须先保存当前成果。用户点击一次，ProductControl 负责停止确认、固定此次保存范围、调用现有 SaveMap 并跟踪其后台处理，再交接定位与导航。
- 本次切换使用这次保存实际产出的 MapIdentity；不能看到任意旧保存任务成功就切换，也不能悄悄使用遗漏最新建图内容的旧地图。
- 地图命名与提交沿用现有规则，不隐式覆盖无关地图。处理失败时保留原始存档和建图上下文，显示失败阶段，可从已保存原始数据重试。
- 切回建图恢复当前进程保留的那份档案，新增关键帧沿用原有编号、原始位姿和回环图。不自动开始新图。
- 切换期间机器人停止，传感器和 LIO 继续处理。服务不重启不等于任何数据都不能重建：地图身份/坐标改变时，局部避障观测需要刷新，就等新观测就绪。

### 源码确认的阻碍

| 位置 | 当前行为 | 热切必须处理的事 |
| --- | --- | --- |
| `real/switch.py`、`sim/switch.py` | 切换按新的 RunPlan、Product 会话和进程启动流程执行；real 只接受 cold_restart | 仍由 ProductControl 选择支持的热切路径，保留现有锁、结果、地图身份和失败处理；real/sim 不合并成通用事务框架 |
| `run_plan.py::managed_processes`、`real/systemd.py::transition` | mode 进程进入停止列表，persistent 可以保留 | 在热切能力与会话接线完成后使用保留路径；仅改 lifecycle 不会更新存活服务的启动环境 |
| `ltlio.cpp::setMode` | 不重建整个前端/回环图，但先改 mode，再尝试加载地图；失败也可能留下新 mode | 先准备候选地图及对齐，成功后在 SLAM 所属线程提交模式；失败保留原来的有效状态 |
| `ltlio.cpp::recordPatchSnapshot`、轨迹记录 | 普通定位扫描也会追加档案；patch 超上限会 pop_front，轨迹超过 10000 条会移除前部 | 冻结原建图档案及轨迹，导航期间不能用环形缓存逐步覆盖它们；核对已有定位模式保存调用者后调整，不能盲删其他用途 |
| `ltlio.cpp::loadMap` | 建地图索引后清除 map/LIO 对齐，并进入等待重定位 | 保留 IMU 初始化、连续 odom 和前端局部配准状态；当前位姿可作新地图配准初值，不能将已有连续里程计当作已验证地图定位 |
| `ltlio.cpp::mapGeometrySnapshot` | 非建图模式会清理导出目录，清理还可能等待后台导出 | 交接前处理已发出的几何任务；暂停发布与销毁建图上下文分开，避免待消费快照被删除或主线程被阻塞 |
| `cyclone_runtime.cpp` | runtime_mode 是启动常量；保存校验从进程环境读取 Product/session；观测绑定地图 ID/epoch | 增加明确的模式/运行绑定控制，状态、保存权限、周期匹配和 MapObservation 都读取实际已提交绑定 |
| `mapd/main.cpp`、`mapd/save.cpp` | Product/session 与保存权限由启动配置决定 | 在线绑定当前 Product/session 与保存能力；先结束相关保存作业，再改变归属 |
| `mapd/engine.cpp::SetReferenceMap` | 切换参考地图会使当前快照失效，下个新观测重置相关状态 | 复用地图激活与 ACK，保持新鲜观测检查；不为了无缝显示把旧碰撞图伪装成新地图数据 |
| `nav/main.cpp` | 全局地图路径、地图身份、控制模式和若干配置在初始化中固定 | 扩展上一轮的后台准备/停止确认/替换方式，覆盖控制模式、全局地图绑定、执行器、输入要求与状态；只切局部算法并不足够 |
| `assembly/host/`、`real/host.py` | map 与 nav 的 Host 模块图不同，当前启动时 build 一次 | 先对这对模式定义共同的基础模块装配；切换由目标 RunPlan 更新模块实际工作状态和会话，不另写通用模块热卸载系统 |

保存代码也在持续变化：当前 `SaveComputeState`/`pollSaveMapAsync` 保留的是保存点云结果，不能依赖旧文档中的“保存结束就已经装好重定位器”。实现时按实际目标地图版本准备索引。

### 哪些保留，哪些变

| 服务 | 保留 | 在线改变 |
| --- | --- | --- |
| LiDAR/IMU | 连接、时间戳、采集流 | 在设备配置相同的条件下不需要改工作方式 |
| slamd | 同一个 LIO 前端、连续估计、原关键帧档案、回环图 | 是否继续追加建图记录、使用的定位地图及其实际对齐、Product 会话绑定 |
| mapd | 同一个服务与地图存储 | 保存权限、参考地图身份；必要时刷新实时三维观测 |
| navd | 同一个进程、最终命令发布者 | 遥控/自主控制模式、目标地图绑定、执行配置；旧任务保持终止 |
| driver | 同一硬件连接及机器人限制 | 原命令发布者维持零输出后继续；不再因工作模式重新初始化驱动 |
| Host/Gateway | HTTP 服务及共同基础模块 | 当前 RunPlan、能力、状态与会话；只运行当前模式需要的业务 |

这能减少重复初始化和建图后台的空闲计算，但保留可续建历史仍然占内存。不能一边承诺返回原图继续建图，一边把关键帧/回环图全部释放。保持一份档案和一张图，不复制两套 SLAM；峰值内存必须实测。

### 两个方向的具体顺序

**建图 → 导航：**

1. ProductControl 检查同一机器人/环境/标定及保存目标；正常保存或录制作业仍按现有归属约束处理。此时仍属于原建图 Product 会话。
2. 停止当前任务并取得停止确认，阻止新的运动任务。
3. 在明确的观测位置停止追加建图档案；LIO/IMU继续。完成已投递的回环工作与相关地图几何交接，保留冻结后的建图历史。
4. 调用 mapd 现有 SaveMap，使用 `auto_process=true`。先持久化当前原始点云、轨迹和关键帧，再由现有后台队列处理。ProductControl 跟踪本次 job_id；前端只展示进度，不负责在任务完成后另发一次切换。
5. 等待该任务生成必需的导航产物并完成校验、正式提交。仅有 `source_saved`/`CAPTURED` 不足以切导航。失败或取消则留在建图模式，保留原始存档并恢复可用的建图记录；不会自动开始运动。
6. 从实际产出的地图取得准确 MapIdentity，完成目标 RunPlan 的一次解析和发布。后台准备定位索引与全局规划数据，用当前估计和已知地图关系作初值确认对齐；不能把保存完成当作定位已成功。
7. slamd 提交定位模式与地图绑定；mapd 激活同一 MapIdentity；navd 切换自主导航配置，Host 更新对应运行绑定。各自 ACK 与新鲜状态属于同一个目标 Product 会话。
8. 全部就绪后 ProductControl 提交 current 记录并显示导航就绪。旧运动任务不自动恢复；用户可以发新目标。

### 保存后的自动后台处理：已有能力与待接工作

2026-11-08 再核对当前代码：

- `gateway/schemas.py::MapSaveRequest.auto_process` 默认 true；同步 SDK 与 Web API 的 saveMap 也默认 true。
- `web/src/components/MapView.tsx` 已有默认勾选的“保存点云后自动后台处理”。普通保存等待到原始数据存档即可结束前台等待，后台进度在保存记录中显示。
- `maps/cpp/save.cpp::ProvideSnapshot` 在原始快照落盘并记录任务后，把自动处理任务置为 QUEUED，交给现有队列。关闭自动处理时为 CAPTURED，可由 ProcessSaveMap 从已有存档开始。
- 后台先处理几何优化结果：正式在线 SAM 快照已有校正时复用；其他输入按已有条件进行离线优化或报告跳过，不宣称每次都重新闭环。
- 然后按配置清理动态点、生成必需的三维导航产物（当前默认含 OctoMap）、校验并提交地图包。ESDF 等未要求的产物不因此全部启用。
- 原始存档与处理产物分开，处理失败仍可报告原始数据已保存，并从存档重试。

因此不用新增第二套 Python 后台队列。待补的是 ProductControl 自动发起保存并等待这一项任务，以及成功后的热切交接。保存任务中途仍使用原建图会话；完成前不重启 mapd/SLAM 或改掉保存所属会话。

本轮定向运行 `test_save_map_accepts_the_validated_http_request` 的两种设置，2 项通过，确认 HTTP 请求把 auto_process 原样交给 mapd 且默认 true。这是接口测试，不是后台完整处理或实机热切验收。

对用户区分四个进度：**正在保存 → 原始数据已保存，正在后台处理 → 导航地图已生成，正在交接 → 导航就绪**。普通保存只走前三者中的保存/处理部分，完成后仍留在建图。后台工作不等于零耗时，也不证明对目标机实时感知没有影响，需测处理时长与资源占用。

**导航 → 继续建图：**

1. 停止导航任务并确认，禁止自动恢复旧目标。
2. 确认原建图档案仍属于同一连续 SLAM 过程：没有 reset、时间跳变造成上下文失效，也没有换成另一份无关地图。
3. 结束/失效化在途定位匹配结果，保证它们不会在恢复建图后再次改变对齐；保留当前连续估计。核对保留图的坐标关系后恢复原档案追加与回环工作。
4. mapd 恢复建图保存权限和当前观测绑定；navd 回到建图所用控制模式；Host 更新状态/能力。
5. ProductControl 提交建图模式；新扫描、原档案和之后保存的地图属于同一份续建结果。

当前位置失效而原建图上下文仍有效时，先自动重定位，再恢复追加，不把定位丢失直接等同于档案丢失。无法恢复原建图数据时，说明本次不能续建原图，不以空图冒充续建。现有 3000 关键帧上限仍要如实报告，不能靠切换模式清零计数绕过容量语义。

### 会话与失败处理

- 仍只用 `product_session_id` 标识一次 Product run。新的目标 RunPlan 仍为不可变文件，不原地改写旧计划，不增设公开 mapping_session_id。
- 进程 PID/boot ID、LIO source epoch、地图 content epoch 各有现有含义；切 Product 不应自动等于重置传感器或 LIO。
- 需要 Product/session 的 slamd、mapd、navd、Host 明确接收并确认新的绑定。只依赖物理配置的采集/驱动服务不额外增加无用途的模式状态。
- 热切失败按实际已完成的服务动作回退，保留建图上下文及零输出；不能直接调用会重启所有服务的冷切回滚冒充无损恢复。
- 无法完整回退时保持停止，报告哪些服务已改变。下一次操作依据真实状态处理，不把几个服务的部分成功报告成切换完成。

## 每阶段所需验证

1. 生命周期测试：承诺保留的进程 PID/boot ID 不变，新会话 readiness 正确；若失败，修会话绑定或继续将该服务留在重启范围。
2. SLAM 回放：切换前后点云/IMU持续输入，map/odom/body 关系符合保存地图的实际对齐；若出现错误跳变，修正地图与估计器交接，不靠放宽容差通过。
3. 导航契约：交接期间运动保持停止，地图与定位就绪后才接任务；失败报告真实阶段且不意外恢复旧运动。
4. 算法切换：旧计算结果不能覆盖新后端轨迹，首条新命令基于当前状态；失败则保持停止并报告原因。
5. 实机对比：同一平台、同一地图比较切换耗时、位姿中断和CPU/RAM，不以本地单测声称实机无缝。

## 本轮局部算法切换接口

`POST /api/v1/navigation/planner`，请求 `{"name":"cmu","request_id":"planner-1","client_id":"sdk"}`；同步/异步 SDK 均为 `robot.navigation.select_planner("cmu")`。

仅导航控制模式支持。当前任务（含暂停任务）、巡检、滚动任务和人工控制权需先结束。选择范围取 Product 与 env 已声明算法的交集；CMU 还需要该机器人已有的路径库。后台准备新 Executor/Planner，复用停止确认后才整体替换；旧算法不随准备失败而丢失。切换过程中不接收新的运动任务，停止/急停可以取消交接。成功 ACK 表示算法替换完成，不代表地图、定位或运动输入已就绪；新任务仍走原有输入检查。

不增加后台模式管理器，不启动双算法持续计算；100 Hz 控制频率不热改。算法专用规划/跟踪配置与输入策略一起更新，共享传感器处理和机器人标定保持本次进程的配置。客户端和 navd 的 DDS 类型需成套重建后部署。本地验证结果另见同目录交付记录；没有实机部署。

## 当前重定位何时启动

- 保存地图：Gateway 发 mapd 的 `save_map` 作业，不调用模式切换或重定位。
- 实机进入定位 Product：`real/backend.py::complete_localization_handover` 调用 `_relocalize`，执行 `slamctl track-against-map`；`relocalize` 开关决定是否带给定初始位姿，不代表 false 就跳过这一步。
- SLAM 接受 `track_against_map` 后，等待新的有效扫描，再异步匹配地图。优先使用请求初始位姿/有效历史种子；没有可用对齐信息时需要全局搜索。
- 当前公共配置实机周期 5 秒；仿真覆盖为 0，成功后停止周期重匹配。周期匹配不是每次都做全局搜索。连续几何拒绝 3 次会清除旧种子；没有 map/odom 对齐且失败过时也会较早升级全局搜索。缺扫描或扫描陈旧只记等待，不算几何失败。
- 人工 `seeded_relocalize` / `global_relocalize` 可以显式触发。`loadMap` 会撤销旧地图对齐，但加载成功本身不等于定位成功。
