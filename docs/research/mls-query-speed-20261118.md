# MLS 全局查询提速：lazy A* 与跨查询复用

核对日期为 2026-11-18。本页记录全局查询慢在哪、去掉几何检查的实验、本次两项改动，以及留给后续的工作。所有数据来自本地合成场景和 Rust 查询本身，未经过 SCAN、MuJoCo 或真机。

## 时间花在哪

查询按 Thunder 正式参数运行：0.05 m 分辨率，双圆柱机身半径 0.32 m、前后偏移 0.23 m，上下净空 0.35/0.05 m，支撑高度 0.435 m，最大台阶 0.45 m，坡度上限 tan30°。

在合成坡道上给查询加计数后（插桩副本，不在仓库中）：

| 场景 | 查询 | 几何检查 | 其中被拒 | 检查占总时间 |
|---|---:|---:|---:|---:|
| 30° 坡，宽 2 m，升 2 m | 约 0.1 s | 2,624 | 0 | 约 75–85% |
| 35° 坡，同尺寸 | 约 3 s | 57,456 | 38,078 | 约 91% |

35° 坡上，稀疏图里沿坡直上的边超过坡度上限，查询落到全图 detour 搜索。这个阶段每展开一格看约 200 个邻居，最长跳边约 0.9 m，每条都做一次双圆柱扫掠。38,078 次拒绝全部是“机身撞占据”：前圆柱伸出约 0.55 m，0.55 × tan35° ≈ 0.385 m，正好等于机身底面余量 0.435 − 0.05 m，全局模型又不随坡面俯仰。

改动前，一次查询内的检查结果用 `admitted` 缓存，下一次查询全部重算。同图同端点再查，检查次数和耗时与首次相同。

## 去掉几何检查会怎样

同一份查询把边检查全部返回“允许”，最后仍用完整检查器复核返回的路线：

| 场景 | 现状 | 不检查 | 不检查的路线 |
|---|---:|---:|---|
| 30° 坡 | 73 ms | 4.7 ms | 通过，本来就没有拒绝 |
| 35° 坡 | 2,978 ms | 165 ms | 22 段里 6 段与坡面重叠，最大约 3.5 cm |
| 楼梯 8 × 0.15 m | 856 ms | 90 ms | 25 段里 4 段与台阶重叠，最大约 1.8 cm |
| 墙上 0.5 m 窄缝 | 92 ms | 2 ms | 直接穿过窄缝，机身直径 0.64 m，一侧重叠约 5–10 cm |

重叠深度由独立 Python 计算估出，用的是同一机身尺寸。只有窄缝是任何模型下都过不去的真碰撞。楼梯和坡道的厘米级重叠落在模型本身的误差范围内：体素按整格算占据，机身不随坡俯仰，`support_height` 0.435 m 尚未实测。因此结论是检查不能去掉，但这两类厘米级拒绝属于建模余量问题，需要单独取证。

这不等于 DimOS 会在它自己的机器人上撞。2026-11-16 的同图对比是把 DimOS 地面路线加 0.435 m 后用 Thunder 尺寸复核，四图中 stairs、multifloor 被拒；DimOS 面向 Go2，机身更窄，后面还有局部规划。[同图对比](dimos-latest-repro-20261116.md)

## 本次改动

**lazy A*（`query.rs::surface_search`）。** 邻居入队时不检查，出队并要定下该格时才检查这条边。最便宜的父节点可能被拒，所以每个候选父节点都保留在队列中，定下的代价与逐边检查相同。已知被拒的边不再入队。等代价时可能选出另一条等长路线。

**跨查询复用（`lib.rs::lt_mls_artifact_query_metric`）。** `PlannerState` 保存表面格对的准入结果，下一次查询在下列输入完全相同时复用：

- 分辨率、机身半径与偏移、上下净空、支撑高度与容差、深度与 patch、台阶与坡度、`ground_support`、`direct_support_only`、地图范围；
- no-go 区域和 preblocked 格子；
- 开启 start exemption 时还包括起点位姿和朝向。

起终点接入边（kind 1/2）和以实际起点为起点的边每次单独检查。`set_geometry` 和 `update_region` 与 `query_surface`、`geometry_index` 在同一处清空复用结果。条目超过 500,000 条（约 20–30 MB）时清空，避免长时间运行的大地图无限增长。被取消的检查不写入。

ABI、C 头文件和 C++ 调用方不变。

## 结果

同一台机器、同一份 `query_speed_scenes` 基准，改动前用 HEAD `9ddccf3` 的源码，各跑一次：

| 场景 | 首次 改动前 → 后 | 重复 改动前 → 后 | 路线复核 | 路线长度 |
|---|---:|---:|---|---:|
| 30° 坡 | 92 → 94 ms | 74 → 6.5 ms | 通过 | 6.972 m 不变 |
| 35° 坡 | 2,923 → 1,059 ms | 3,038 → 309 ms | 通过 | 5.824 m 不变 |
| 楼梯 | 931 → 209 ms | 923 → 104 ms | 通过 | 4.683 m 不变 |
| 窄缝 | 135 → 154 ms | 97 → 8.6 ms | 通过 | 7.650 m 不变 |

此前插桩副本每项取 5 次中位数的 A/B 结果一致：lazy 使 35° 坡和楼梯首次查询的检查次数降到 37% 和 20%；复用使重复查询快 9–14 倍。按折线比较，30° 坡、35° 坡和楼梯改动前后是同一条线，只是中间取点不同（例如 30° 坡 71 个点变成 81 个）；窄缝最多相差 0.05 m，即一格。路线都通过复核，长度不变。

重跑基准：

```bash
cargo test --release --manifest-path src/kernels/nav/mls_core/Cargo.toml --lib query_speed -- --ignored --nocapture
```

## 待解决

按优先级排列，接手时先看前三项。

1. **坡度上限可以被原地折返绕过（改动前就存在）。** 合成坡道扫描 15–33°：≤27° 路线干净；28–31° 沿坡直上并出现 8–24 处“前进 0.10 m、后退 0.05 m”的折返；33° 起才走之字。31° 坡超过 30° 上限，原始路线仍沿坡直上，每段坡度都只有 26.6°，逐段检查全部通过，但机器人朝向的地形是 31°，整体爬升 30.7°。同一检查器的贪心平滑后仍剩一处折返，整体 30.3°。HEAD `9ddccf3` 的原版代码在 28°、31°、32° 上得到相同结果。原因是坡度只按相邻两点的高差/水平距离检查，量化后的表面格在上限附近时高时低，搜索用后退一格来凑出合规的单段。修复方向需要讨论：按行进方向的地形坡度检查，或在搜索中禁止短距离内的反向。这改的是运动安全规则，需按 AGENTS.md 与上游对照并留证据。
2. **重跑楼梯矩阵和保存地图回归。** lazy 会在等代价时换路，必须用 `build/mls-unified-20261116/` 的 16 场景矩阵和 `build/mls-limits-20261116/` 的边界图确认结果不变或只有等长差异。这些输入不在仓库中，需要有原始 `build/` 的机器。
3. **30° 坡原始路线的 20 处折返能否被生产平滑消掉。** 同一检查器的贪心捷径在 30° 坡上能消掉、在 31° 坡上不能；尚未在 C++ `smoothRoute` 上确认。见第 1 项。
4. **确认生产是否开启 start exemption。** 开启时复用键包含起点位姿，机器人移动后每次重规划都无法复用。若现场常开，下一步是只让机身体积与豁免区域相交的格对随起点失效。
5. **重复查询仍比 DimOS 慢。** 楼梯约 100 ms、35° 坡约 300 ms，主要是 detour 搜索本身和起终点 24 格窗口内的展开（各约 2,500 格）。DimOS warm query 为 0.4–6.6 ms。
6. **陡坡上机身不随坡俯仰。** 35° 坡的拒绝全部是毫米到厘米级重叠。改模型属于安全模型变更，需要 MuJoCo 或真机证据，并与固定版本上游对照记录。
7. **实测 `support_height`。** 0.435 m 来自模型站姿估计，楼梯与坡道的厘米级拒绝对它敏感。
8. **原报告 35° 坡 77 s 的输入没有复现。** 本地同类场景约 3 s，原地图不在仓库中。
9. **复用上限 500,000 条未在大地图上验证。** 需要在目标 Jetson 上观察长时间运行的内存。
10. `src/kernels/catalog.py` 未列出 `mls_core`、`pose_graph_opt`。
11. `web/public/assets/robots/go2/meshes/mid360_ground_mount/*.dae` 在 `.gitattributes` 中声明为 LFS，但仓库存的是原始 XML，克隆后显示为已修改。需要选择迁移到 LFS 或移除该规则。
