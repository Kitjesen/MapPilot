## 对话控制目标与功能范围（2026-10-20）

本节根据森哥的目标补齐用户功能视角：**用户通过对话表达目标，在一个已经装配所需能力的 Product 中直接开始跟随、搜寻或前往地点；系统持续执行、如实报告，用户能够打断、纠正和接管。** 不要求用户先手动选择“跟随模式/搜寻模式”，也不让模型自行切换部署环境或管理原生进程。Product/RunPlan 的装配与启停仍归 ProductControl。

前一轮人物识别与跟踪修复只是观测、身份和取消链的底层切片，不代表整个对话控制闭环已经完成。整体入口继续复用 Agent；跟随、找物和导航继续使用已有领域执行者。论文与人物修复细节见 [人物开发参考](person-tracking-development-reference.md)，本节定义它们服务的使用结果，不新建任务引擎。

### 执行时应有的共同含义

1. 一句新指令先区分只读问答、观察和移动任务。理解充分、目标明确、能力就绪时直接受理执行；只有目标歧义或缺少必要条件时才请求补充信息，不每步重复询问。
2. “跟随我”先确认目标身份；“搜寻”绑定要找的目标和允许的搜索范围/时限。当前视野没有目标时进入已有搜索链，而不是随意选择最近的人/物。搜索区间、时间和丢失恢复约束使用选定产品/任务的有界参数，具体数值由测量确定。
3. 持续任务保留同一 run 和领域任务引用。短时丢失、重识别和导航受阻是执行阶段，不代表成功结束；持续跟随不因一次导航到达就完成。
4. 明确停止/取消必须能通过专门控制入口及时处理，不等待长模型请求；模型回复、取消 ACK 和任务终态不能替代原生物理停止证据。紧急停止继续由已有独立控制面负责。
5. “暂停”必须先定义保留哪些身份/搜索进度、怎样停止子目标、恢复时重验哪些当前证据。尚未实现的领域明确报告不支持，不把 cancel 改一个标签当作 pause。
6. 改目标或改任务时收敛旧执行，再建立新的执行归属；人工接管、相机失效、定位失效或网络模型不可用时，由对应 owner 决定暂停运动/取消/报告，而不是依赖下一轮语言推理。

2026-10-20 首轮控制改动已完成本地验收：网页 [useInstructionTask](../../web/src/hooks/useInstructionTask.ts) 在任务运行时保留输入；HTTP/MCP 由 Agent owner 识别完整控制话语，查询、保持当前任务和取消复用原 `run_id`，普通新任务仍被活动任务所有权及运动就绪门控约束。换任务采用取消旧任务、等待领域停止确认、重新提交的顺序，不自动排队。暂停/恢复明确返回不支持，多轮目标纠正仍待实现。HTTP `/stop` 是锁存软件急停；任务 cancel、导航任务 pause/resume、人工保持解除是不同操作，不能统一映射为它。导航保持解除明确不恢复旧运动。语音打断同样要遵守这些区别。

森哥确认设备未开机后，本地继续补齐空闲与终态查询、聊天事实回执、HTTP 409 具体拒绝原因，
以及成功任务取消不得改写完成结果。网页在状态缺失/过期或仍持有活动任务时发送
`control_only=true`：同一文字入口仍可查询和结束，但服务端不得启动新任务。
这保留浏览器既有运动事实约束，不能把它与服务端 lease/estop 检查当成等价。

### 已确认的任务切换交互（2026-10-21，待实现）

森哥在逐步讨论代码方案时确认：**始终只有一个正在执行的运动任务；允许随时通过
对话修改意图；新目标明确时直接切换，有歧义时才询问，不对明确目标增加一次确认。**

目标明确后的执行顺序为：确认具体新目标 → 请求结束旧任务并取得所需停止确认 →
启动新任务 → 返回真实切换结果。语言模型表示理解不等于视觉目标已经确定；目标选择
仍由对应感知／领域能力提供证据。停止回执与电机物理停稳继续保留各自含义。

网页的 TypeScript 请求函数和 Python SDK 都封装同一个 HTTP API，底层后端和任务逻辑
只有一套；SDK 是便于其他程序调用的客户端库，不是网页请求必须经过的后端服务。
API 接纳／转发请求，现有 Agent owner
负责当前意图、任务归属及交接；Follow／找物／导航负责领域执行。前端或 SDK 不应
自行拼接取消、新建调用来充当可靠的切换管理者。任务切换发生在已经装配所需能力的
同一 Product 中，不借此新增 Product 生命周期实现。

10-21 SDK 薄封装已补齐现有 HTTP 契约，同步与异步客户端提供相同接口：

- `send_instruction(text, *, run_id=None, control_only=False, request_id=None, client_id="sdk")`：
  原样传递文字与控制参数；`control_only=True` 仍由后端约束为不得启动新任务。
- `get_agent_run(run_id)`：查询当前 Host 保留的指定 run，原样返回 `found=false` 及原因。
- `cancel_agent_run(run_id, *, request_id=None, client_id="sdk")`：仅请求取消指定 run。
  请求体遵守现有 API，不额外加入 Follow 的 `reason` 参数或客户端交接策略。

`CommandResult` 增加直接可读的 `run_id`，其他 Agent 状态、具体拒绝原因和停止确认
保留在 `raw`／查询字典中。`go_to(text)` 保留原调用方式并复用文字入口。
GET 的 HTTP／网络错误继续抛异常，POST 拒绝／网络错误继续返回既有失败回执；
连接失败不改写成任务不存在，不自动重试。已有导航取消、软件急停和 Follow 专用接口
继续保持各自含义。

新增 32 项同步／异步契约测试通过，包含真实 Gateway 路由的查询与定向取消往返；
SDK 全范围回归 137 项及 21 个 subtests 通过，其中包含上述 32 项，不重复累计。
坏身份不会取消当前任务，取消受理不等于停止确认。受影响文件 Ruff 及独立代码审阅通过。
证据保存在 `build/sdk-agent-contract-20261021/`。本切片只证明客户端契约，
未实现目标自动切换、多轮澄清、客户端断线恢复或实机运动资格。

当前代码仍采用 10-20 的首轮规则：活动任务拒绝普通新任务，操作者先取消并确认
停止后重新提交。**本节记录的是已确认的产品行为，自动切换与多轮澄清尚未实现。**
森哥进一步确认：明确要求更换目标但存在歧义时，**先停止旧运动，再询问具体目标**。
后端保留这次更换意图和澄清上下文；等待回答期间不继续跟随旧目标，也不自动恢复
旧运动。得到回答后，根据有效观测确定新目标，再进入新任务的启动条件检查。
这里只确认交互行为；底层采用已有取消／停止能力，不能把尚未实现的 Follow pause

### 最小验收场景

首个可用版本至少能演示：唯一正确人物直接跟随；多人“我”有明确绑定；目标交叉/遮挡不换人；搜寻不在视野的对象并复核；找到后按指令报告或进入后继动作；执行中停止/换任务；导航受阻或定位/相机异常时给出真实原因；人工接管后不抢回控制；同一任务的迟到结果不会影响新任务。

## 1. 目标和完成标准

下一阶段要让一句自然语言指令产生可追踪的真实执行，而不是只得到解析结果或语言回复。
Agent 的 `run_id` 应关联它实际启动的 Follow、导航或巡检任务，等待执行者给出的结果，
并且只取消自己拥有的子任务。Web、SDK 和 MCP 通过相同领域接口看到一致事实。

完成后的最小闭环是：

1. 用户提交指令，得到一个可查询、可定向取消的 Agent `run_id`。
2. Agent 启动领域任务后保存其真实任务引用，而不是只记录“工具调用过”。
3. 领域任务的受理、执行、业务结果和运动证据分别呈现。
4. Agent 只在所需子任务真实成功后报告完成；未知、超时和未找到都不能变成成功。
5. 旧 Agent、旧 Follow 和迟到事件不能改变后启动的执行。
6. Host 重启后不自动重放运动；无法恢复的进程内任务明确报告不可用或状态未知。

## 2. 保持不变的边界

- ProductControl 继续拥有 Product、RunPlan、进程、就绪和地图激活。
- 原生导航继续拥有规划、三维安全检查、运动仲裁和导航终态。
- mapd、SLAM、Inspection Executor、VisualServo 和 Agent 分别维护自己的领域事实。
- `product_session_id` 标识一次 Product 运行，不能被 Agent `run_id` 或领域任务 ID 代替。
- Gateway、MCP、SDK 和网页只适配协议及展示，不推进另一份任务状态机。
- 第一轮不增加通用 Mission 引擎、全局任务表、任务数据库或新的后台进程。
- 第一轮不迁移 HTTP/DDS，也不因接口命名统一而搬迁现有目录。
- 历史记录由各所有者按实际需要保留，不建立跨领域永久事件库。

## 4. 实施阶段

### 阶段 0：先固定相机与共同观测契约

结果：Follow、Agent 和记忆使用同一次观测中的图像、对象、位姿与地图身份。
沿用现有相机采集、SynchronizedFrame 和 PerceptionOutcome，不新建感知服务或同步框架。

主要改动位置：

- 原生相机、Host 适配与 `src/runtime/msgs/sensor.py`：保留每流来源序号，补可靠的生产者重启代次；
  不把共享内存创建时间当成进程身份，也不把不同流的相同序号当成 RGB-D 配对证明。
  明确时间含义、深度单位和配准状态。
- `src/perception/frames.py`：保留各输入时间、固定变换和当时有效的地图身份。
- `src/runtime/msgs/` 与 `src/perception/module.py`：一次发布绑定 Product session 的最小观测快照，
  复用已有计算结果；只提供 detection/track 来源身份，稳定人物身份仍归 Follow。
- `src/decision/modules/visual_servo.py`：先消费共同观测，删除重复配对逻辑，保留多视角及三次有效观测核验。
- 现有标定检查和能力呈现：复用检查结果，区分可看图与可使用世界三维坐标；最终运动仍由原生导航决定。
- 随后迁移需要共同证据的 Agent 和记忆，按 `map_id + content_epoch` 隔离空间记录。

验收场景：

- 推理期间机器人移动，投影仍使用原观测位姿，不与完成时最新位姿混合。
- 检测结果迟到、源重连或地图切换时，旧观测不能贴上新来源或新地图身份。
- 重复同帧不能计作三次身份核验；有效负观测与深度/输入失效可区分。
- 只有 RGB 或标定未验证时可展示观测，不能据此发布合格三维运动目标。
- 换地图后可以查询旧文字线索，但不能把旧地图对象坐标用于当前导航。

RealSense 当前使用主机收到帧组的时间，不能称作曝光时间。Orbbec 配准和时间语义需按
实际适配核对。字段与本地测试通过不代表硬件标定、时间同步或原生运动已经通过。

### 阶段 A：Agent 关联真实领域任务

结果：一个 AgentRun 能列出并等待自己拥有的领域任务，取消时只收敛这些任务。

当前 tracking 没有装配完整 Agent/SemanticPlanner，inspection 的 semantic_planning
装配具备组合入口。先在实际声明这些能力的 Product 上验证；需要 tracking 承载 Agent 时
再显式调整能力和依赖，不能把配置了 LLM 型号当作 Agent 已就绪。
inspection 的 Agent/SemanticPlanner 目前通过可选导入装配且不属于 critical_modules，
因此验收前还需明确检查两者已装配且 ready，不能只看 Product ready。

主要改动位置：

- `src/decision/modules/agent_planner.py`：在现有 `AgentRun` 中保存有序的子任务引用和结果。
- `src/decision/modules/semantic_planner.py`：返回明确的领域任务引用，不用字符串暗示成功。
- `src/decision/modules/visual_servo.py`：复用现有 Follow 查询/取消，不增加第二套生命周期。
- `src/lingtu/assembly/host/wiring/semantic.py`：只补实际需要的强类型反馈接线。
- `tests/decision/test_agent_task_lifecycle.py`：覆盖父子归属、等待和定向取消。

最小数据只包含领域种类、`product_session_id`、领域任务 ID、状态和结果。
不先创建公共 Task 基类；只有导航、Follow、巡检中的第二个真实调用方需要同一逻辑时，
才把那一小段结构放入已有共享契约位置。

验收场景：

- Agent A 启动 Follow F1，状态中能查到 F1 的真实引用。
- 取消 Agent A 时先冻结新工具调用，再取消 F1；收到匹配终态后才结束 Agent A。
- Agent B 或操作者随后启动 F2；A 的迟到取消、回复和 F1 终态不能影响 F2。
- Agent 启动的导航被外部接管时，Agent 报告 `superseded`，不能报告到达。
- Agent 进程重启后不自动重发旧 Follow 或导航；旧 `run_id` 不伪造成已恢复。

### 阶段 B：让“找到一瓶水”具有可验证结果

结果：语言理解、场景感知、对象定位和导航执行形成一条有证据的链。

主要改动位置：

- `src/decision/tasks/decomposition.py`：保持任务描述职责，不在描述对象里复制运行状态机。
- `src/decision/modules/agent_planner.py`：编排查找能力并记录实际结果，不另写一套搜索/导航状态机。
- `src/decision/modules/semantic_planner.py`：只接受新鲜、地图坐标有效且可导航的对象候选。
- 场景图和对象记忆的现有所有者：提供对象 ID、类别、时间、地图位置和来源观测。
- 对应 decision/perception 测试：使用明确观测构造成功、未找到、陈旧和歧义场景。

“找到”至少需要新鲜感知证据、目标类别匹配、有效地图位置和最终近距离复核。
语言模型可以提出类别、属性和关系约束，但不能生成对象位置或决定已经找到。
若只有旧记忆、低可信候选或无有效深度，结果应是候选不足或需要继续搜索。

验收场景：

- 场景中存在新鲜水瓶观测时，Agent 记录其对象身份和观测来源，再提交导航子任务。
- 到达候选位置但最终画面没有水瓶时，本次查找失败或继续探索，不能宣布成功。
- 两个相似瓶子同时存在时，执行记录保存被选对象，后续观测不能悄悄换成另一对象。
- 只有记忆匹配、没有当前可导航证据时，可以提示历史线索，但不发出未经验证的运动目标。
- 数据集或回放验证只能证明算法链路；不得写成仿真或实机已经通过。

### 阶段 C：统一 Web、SDK 和 MCP 的领域语义

结果：三个入口调用相同执行者，返回相同任务引用、状态、可用操作和拒绝原因。

主要改动位置：

- `src/gateway/routes/commands.py` 与现有领域路由：保持薄适配，不持有执行状态。
- `src/lingtu/sdk/client.py`、`async_client.py`：补 Follow 和 Agent 的按引用查询、取消。
- MCP 技能注册：复用领域 owner 的开始、查询和取消方法。
- `web/src/services` 与任务卡：展示任务、视觉阶段、业务结果和运动事实。
- `docs/api.md`：给出同一场景在三个入口中的请求与结果含义。

验收场景：

- Web 启动 F1，SDK 使用 F1 引用查询，MCP 使用同一引用取消，看到相同终态。
- 不支持暂停的 Follow 不在任何入口公布暂停操作。
- Product 切换后，旧 session 的修改请求在所有入口都被拒绝，历史查询保留真实结果。
- 网络重连后通过查询恢复显示；重连本身不能触发 start 重试或任务恢复。

### 阶段 D：复用巡检作为多步骤任务模板

结果：Agent 可以启动已有 Route 执行并读取逐点导航、采集和报告结果。

主要改动位置：

- 现有 Inspection service/Gateway 生命周期：保留原生 Executor 为唯一推进者。
- Agent：只保存巡检 `task_id`，等待原生任务和采集结果，不逐点发送导航命令。
- 巡检报告接口：区分拍摄完成、分析完成、未配置分析和任务终止。
- MuJoCo 巡检场景及相关测试：验证契约和动作顺序，不冒充现场证据。

验收场景：三点 `capture:overview` Route 使用固定地图和版本启动；每一点先完成导航和
稳定检查，再产生采集结果。编辑 Route 不改变运行中的快照。取消时不推进下一点，
恢复遵守现有 checkpoint 和显式 resume 条件。

### 阶段 E：仿真与实机资格验证

结果：分层证明接口、算法、仿真运动和实机运动，不混用证据等级。
这些验证随对应阶段推进，不等 A–D 全做完才开始；平台未到位时明确保留未验证项。

验证顺序：

1. 本地契约：父子归属、迟到事件、取消、重启和 Product session 隔离。
2. 数据集/回放：检测、重识别、深度投影、对象关联和三维位置跳变。
3. 原生 MuJoCo：Follow 与查找任务真正产生路径、运动、终态和停止输出。
4. 实机静止：D435i 帧、时间戳、内外参、深度、模型输出和地图坐标一致。
5. 受监督实机运动：低速短距离跟随、离开视野再出现、相似人物干扰和取消停车。

实机放行前的障碍包括板端模型输出正确性、D435i 到机体的完整标定、三维位置稳定、
原生导航就绪以及可关联的停止证据。任何一项未知时都不把本地通过写成实机可用。
连续 Follow 没有自然成功终态；只有用户取消、策略终止或失败，不能因短暂到达子目标
自动显示完成。

### 阶段 F：按测量结果优化传输和性能

协议迁移最后按测量决定；影响有效观测的积压随阶段 0 就处理。分别测量采集/解码、
预处理、检测、特征、网络、排队和任务反馈时延，并记录输入分辨率、硬件、模型与帧龄。
当前远端 observe/embed/chat 共用推理锁，需要验证长 VLM 请求是否让实时检测结果过期，
再选择排队或资源调整；取消和原生控制不能等待长模型推理。只有 HTTP JSON 或 JPEG 编码被证明是主要瓶颈时，
才局部采用二进制流或 gRPC；媒体、任务控制和原生 DDS 不要求使用同一种协议。

## 6. 依赖、风险与停止条件

依赖顺序：先推进阶段 0 的共同观测与 Follow 消费；A 在此基础上关联真实 Follow 任务。
0 中的记忆地图分区可与 A 并行，但 B 必须在观测和记忆的空间依据可用后进行。
C 在 A 的接口稳定后完成；D 可在 A 后独立推进。E 随每个切片提供对应等级的证据；
F 中影响实时有效性的资源问题及时修复，协议迁移只在可重复测量证明必要后进行。

主要风险及处理：

- 同时读取多个“最新值”：共同观测固定采集时间、变换和地图身份，消费者不再次配对。
- 慢推理阻塞快检测：按阶段测帧龄和排队，分开实时观测与低频大模型请求的调度。
- LLM 把文字回复当结果：只认领域执行者终态与感知证据。
- 旧回调污染新任务：按 `run_id`、领域任务 ID 和 `product_session_id` 三者核对。
- 取消范围过大：父任务保存自己的子任务集合，逐项定向取消。
- 感知误认：保存对象身份与多帧来源，接近后再次核验，不用固定显示 ID 掩盖变化。
- 重启后状态不明：明确报告不可恢复，不自动重放运动。
- 架构范围膨胀：每个阶段只补已被真实场景需要的接口，不先建设通用框架。

每阶段在其验收场景可重复通过、文档与行为一致后停止。失败时先修正所属领域，
不通过 Gateway 包装或 Agent 提示词隐藏问题。地图保存/重载、定位和自主导航的 P0
门槛始终独立存在；本计划不能占用或降低那条产品闭环的完成标准。
