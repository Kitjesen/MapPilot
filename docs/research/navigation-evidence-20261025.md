# 深入验证支撑预检，而不扩大导航架构

## 需要回答的唯一问题

新加入的支撑预检，会不会把原本在当前XYZ+yaw离散规则下可达的目标误判成
`support_disconnected`？这与“固定站姿是否覆盖实际步态”是两个独立问题。
本轮先验证前者，不增加运行时地图层、模型管理或安全检查模块。

## 从原始材料入手

| 材料 | 核查内容 | 本轮实际来源/缺口 |
|---|---|---|
| 占据/自由/未知体素与分辨率 | 起点、断口、桥、层高是否与测试条件一致 | 测试从体素直接生成，64份`.ot`保留；这是合成证据，不是新采集的实测地图 |
| 起终点XYZ/yaw、目标容差、支撑高度、坡度、步高、预算 | 两个算法是否回答同一个问题 | 全部由可执行测试源码给定，记录用例ID与结果；没有读取先前成功路径来定答案 |
| URDF collision、安装实测、关节角 | 固定模型是否覆盖腿/附件的实际运动 | 本轮用解析朝向条件隔离搜索；不宣称完成URDF或真实步态验证 |
| 原始LiDAR扫描、射线来源、IMU及标定 | 真实地图的占据、自由和支撑证据是否可信 | 此轮没有新采集；不能由整理后的点云截图代替 |
| 时间戳、实际位姿/关节、下发及实际执行命令、接触记录 | 规划时间、运动时间、跟踪误差是否一致 | 现有Thunder组件物理记录不能作为本轮Go2实机证据 |

单张截图只能辅助观察，清理后的点云不能恢复原本缺失的射线自由空间证据；
漂亮路线和编译成功均不能直接证明真实机器人能够执行。

## 方法与实际工具

1. **约束放宽的逻辑论证**：将完整姿态图记为G4，基础支撑图为G3。当前完整搜索的
   每条平移边都要满足同一XYZ支撑规则，旋转投影到同一XYZ。因此完整路线若存在，
   必须存在相应支撑通路。穷尽G3仍无法到达目标，是当前离散规则下的充分拒绝条件；
   G3可达不是机体通过的充分条件。精确目标与容差终点必须分别保持一致。
2. **独立穷举对照**：新增C++ FIFO广度优先搜索，用`std::deque/std::set`穷尽完整
   XYZ+yaw图。它不调用生产`heading::search`来求答案，不复用其状态类型、启发式、
   支撑预检、搜索缓存或迭代分配。输入仍使用OctoMap和相同底层支撑/解析机体谓词。
   这隔离了搜索剪枝正确性，没有独立验证几何谓词。
3. **反例与变换关系**：8种桥带组合×4种请求/地形×原点和平移后两种场景，共64例。
   包含完整断口、侧向绕桥、朝向门限、非格点目标、无指定yaw、原目标被挡但容差可达、
   台阶高度变化。整图平移后可达性必须不变；地图有完整支撑时必须可达，完整断开时
   必须不可达。另保留已有同XY上下楼层分离的回归。
4. **预算判定检查**：每例再限制为6次总展开，断言总预算不被突破，且不能对穷举
   判为可达的目标报告支撑不连通。预算不足可以返回未完成，不要求低预算找到路线。
5. **可重复执行**：MSVC Release、CMake、CTest与原生OctoMap；原始体素、源码和
   stdout日志保留。已有native-motion CI脚本会运行CTest，本测试注册在同一测试树；
   本轮没有推送或执行远端CI，不能声称CI已通过。

性能分析另用固定输入与同进程交替测量；如继续定位热函数，可用Linux `perf`
或Windows性能记录工具采样，但本轮未运行采样分析器。FCL、外部几何求解器和
实测运动捕捉也未在本轮使用，不以工具名称代替验证结果。

## 当前结果与能证明的范围

- 独立穷举与生产搜索：64/64可达性一致，56可达、8支撑不连通。
- 32组整图平移前后可达性一致。
- 64次小预算检查未出现把可达目标错误报告为支撑不连通。
- 返回路线逐边复查基础支撑与解析机体条件。几何谓词共享，因此不是第二套碰撞
  算法的验证。
- 对照算法没有发现本轮范围内的新运行时缺陷，故未再改生产判定或增加模块。

上述测试不是对所有地图的形式化证明。逻辑论证依赖“G3确为G4的约束放宽图”，
测试验证实现的有限实例；共享支撑函数若有错误，两个搜索仍可能一起给出错误答案。
此外，预检会消耗总预算，有限预算内的成功率与耗时需要单独对照，不能由无限预算
的可达性关系推导。真实运动正确性仍需测量支持的机体包络、独立场景几何和监督实走。

## 他人如何复核

源码：`src/nav/cpp/planning/global/octoplanner/heading_reference.cpp`。
构建目标：`octoplanner3d_heading_reference`，仅在`BUILD_TESTING`启用，不进入导航运行时。

```powershell
cmake --build <已配置的原生构建目录> --config Release --target octoplanner3d_heading_reference
ctest --test-dir <已配置的原生构建目录> -C Release -R octoplanner3d_heading_reference --output-on-failure
# 可选参数保存每例原始体素；stdout包含桥带mask、请求mode、平移标识和双方答案。
<exe路径>/octoplanner3d_heading_reference.exe <新输出目录>/maps
```

原始材料与测试日志：[本轮验证目录](../../build/support-reference-20261025/README.md)。
此前七场景性能对照：[支撑连通性记录](support-connectivity-20261025.md)。

后续物理对照：[支撑与实际运动的 10 组实验](support-gait-20261025.md)。
发现中心支撑及膨胀轮足支撑区域的实际误拒案例；算法之间一致不等于物理定义正确。
