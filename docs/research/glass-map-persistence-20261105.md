# 扫图可见玻璃、保存后消失：当前机制与复现

2026-11-05。用户反馈为“保存完成后当前页面就消失”，不是仅在重新加载或进入导航后发现。
本轮只读追查和隔离合成验证，没有修改产品的删点、射线融合或玻璃策略，也未连接 NX。

后续文件整理将新备份名统一为 `map.before_clean.pcd`，旧 `map.pcd.preclean` 继续兼容。
本文原始复现文件不改名；当前文件归属和失败任务保留规则见

## 性能优化与本问题的关系

上一轮优化移除了重复的落点邻域、自由探针、整图候选统计、表面邻桶查询及一次同卷整包复制。
它没有改变清理阈值或新增玻璃处理。当前正式 prune 与性能优化前保留的 baseline-prune.exe
在以下 13 组合成输入上，完整 JSON 结果 13/13 相同。
这证明这些复现行为在优化前已经存在；不能据此推断现场运行的是哪个部署版本。

## 真实玻璃标签的离线补充验证

使用 3DRef Seq1 的 Hesai 点云和该雷达位姿，在两个各 61 帧、约 6 秒的窗口中，
以首帧全部点构造目标图，用窗口内全部扫描提供射线证据，并运行当前 `prune`：
第一窗 1,098 个玻璃标签点全部保留；第二窗 5,073 个玻璃标签点中有 14 个被删除。
逐点 ID 和生产 `VisibilityEvidence` 的回放核对了这些删除结果。第二窗刻意选取
玻璃点数较多的帧，单帧目标图也不是完整 SLAM 重建；材料标签和估计位姿不等同于
逐点动态真值。因此该比例不是全序列准确率，也不能单独确定 14 点均为静态误删。
输入、标签映射和完整统计见 `build/3dref-prune-labelled-20261105-run1/README.md`。
本次没有运行完整保存事务或验证对应 OctoMap，不能据此归因 Go2/NX 现场现象。

## 第一处：prune 将透射回波视为自由证据

当前 `prune.visibility_surface_v4` 不识别透明材料。
地图点曾有 5 cm 内的近邻命中之后，如果后来累计三个有效自由帧，且没有得到局部表面保护，
它会被删除。有效自由帧要求该点附近七个探针被射线覆盖。
自由帧不必连续；空扫描不增加证据，但也不清零。新的近邻命中会清零，同帧近处命中优先。

正式 prune.exe 的合成结果：

| 输入 | 当前结果 |
| --- | --- |
| 稀疏点先命中 1、2 或 20 帧，之后三帧射线穿过并命中背景 | 删除 |
| 只有空扫描或更近遮挡 | 保留 |
| 每帧同时有近处落点和后方落点 | 保留 |
| 两帧穿透后重新命中，再两帧穿透 | 保留 |
| 同一九点竖直面，只有中心被穿透 | 中心得到邻居保护，全部保留 |
| 同一九点面全部被三帧穿透 | 九点全部删除 |

平面保护要求附近至少六个可靠邻居，且邻居至少命中两帧、`free_frames == 0`。
所以稀疏玻璃、整片透射、或者周围点出现少量自由证据时，保护可能失效。
尤其存在资格不一致：目标点要三帧自由证据才被判矛盾，邻居只出现一帧就不能提供支撑。
简单放宽邻居资格也不能解决整片透射，且需要配对验证真实动态残影的清除。

代码：`src/maps/prune/cpp/core/visibility.cpp`、`src/maps/prune/cpp/cleaner.cpp`。
复现目录：`build/glass-prune-evidence-20261105/`。
`summary.json` 保存 13 组结果，`baseline-comparison.json` 保存优化前后对照。

## 第二处：保留点云不保证 OctoMap 中仍然占据

`PopulateSavedRayOctomap` 使用保留点云来筛选哪些扫描端点仍可产生 hit，
随后按原始扫描逐帧融合 hit/miss。同帧 hit 优先，跨帧仍会累计 miss。
它并未将保留点云的所有格子固定为占据。

隔离原生 probe 直接调用当前正式函数。玻璃标记点在原点前 1 m，背景在它后方 1.5 m，
点云中始终保留这两个点，三组 `dropped_endpoints` 都为零，没有运行 prune。

| 输入 | 玻璃标记格概率 | 状态 |
| --- | ---: | --- |
| 先一次近处命中，后三帧命中后方背景 | 0.4087591295 | free |
| 同帧近处与背景都有命中 | 0.6999999972 | occupied |
| 一次近处命中，之后转扫侧面、不经过原位置 | 0.6999999972 | occupied |

结果：`build/glass-prune-evidence-20261105/ray-probe/result.json`。
实现：`src/maps/include/lingtu/maps/octomap/rays.hpp`。
这是合成输入调用实际原生函数；输入没有玻璃材料标签，不能称为真实玻璃分类验证。

## 当前页面变化仍需区别

当前 `SceneView.confirmSaveMap()` 成功分支只更新保存状态、提示和地图列表，
不直接切换到清理后的 PCD。`map` Product 的显示策略也不会因保存成功自动加载保存地图。
保存点云加载的当前实现下载完整 preview PCD，不能把问题简单归因于“只显示三万点”。
实时扫描叠加由用户偏好控制，不能假定用户看到的一定只是单帧激光。

当前 SLAM `pollSaveMapAsync()` 更新保存快照、边界和重定位器，没有直接改写
`map_cloud_map_`、`global_map_cloud_` 或源 epoch；mapd 未订阅 `saved_map_cloud`。
存在另一条实时替换链：在线图优化完成后 `mapGeometrySnapshot()` 导出校正关键帧，
mapd `InstallGeometry()` 替换累计地图并清空旧实时体素/占据，随后由新扫描补回；
Gateway 对 voxel/accumulated 快照做替换显示。
`startSaveMapAsync()` 会推进并收取在线优化结果，因此两者可能在时间上接近，
但没有该次运行事件日志，不能把这条链确定为用户看到玻璃消失的原因。

因此“保存后立即消失”是重要的时间关联，但当前未取得该次现场版本及玻璃区域的逐阶段数据，
还不能唯一指认是 prune、快照与实时显示的变化，还是 OctoMap 所致。

## 正确的修复边界

玻璃后的真实回波不能无条件证明玻璃所在位置可通行；同时，真实物体移走后的射线也应能清除旧残影。
仅凭相同的 XYZ 近处/远处回波序列，无法可靠区分这两种情况。
单纯提高三帧阈值、永久保护所有曾命中过的点，或者只在 Web 画回玻璃，都不能完成闭环。

已有 SC-04 设计把有边界三维玻璃面及实时/保存射线闭环列为未完成：
`docs/design/slam-scene-adaptation.md` 的 G1/G2。
确认表面需要进入 prune、保存射线、实时占据和保存重载后的实际三维碰撞查询。
真实透明表面、正常物体移除、玻璃门开闭应有配对用例。
现阶段应先核对现场该区域在清理前快照、`map.removed.pcd`、最终 `map.pcd` 和 `octomap.ot`
中的状态，不能把本轮机制复现写成已修复现场玻璃。
