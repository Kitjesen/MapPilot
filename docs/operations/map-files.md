# 地图文件与失败保存任务

本文说明当前正式保存链中的文件归属、名称和保留规则。保存分为点云归档和地图处理：
`source_saved=true` 表示这次任务已有可靠存档，`SUCCEEDED` 表示后续地图处理与提交完成。
两者分别报告；处理失败不会把已经保存的原始存档删掉，也不会发布半成品导航地图。

## 先找哪一份

| 要找的内容 | 位置 | 含义 |
| --- | --- | --- |
| 当前可用地图 | `<地图根目录>/<map_id>/` | 正式提交的地图包，能否导航仍由地图激活检查决定 |
| 本次保存的点云存档 | `.save_jobs/<job_id>/capture/map.pcd` | 本次 SLAM 快照，后续加工不修改；成功、失败和取消后都保留 |
| 清理前的完整点云 | 地图包中的 `map.before_clean.pcd` | 首次应用 prune 前的备份，可能已做配准和图优化 |
| 最近被清理掉的点 | 地图包中的 `map.removed.pcd` | 最近一次 prune 的移除结果，用于检查误删 |
| 保存任务 | `<地图根目录>/.save_jobs/<job_id>/` | 原始归档、状态和事件；可以等待手动处理，也可以追查失败 |
| 完整原始传感器数据 | 独立录制目录 | 原始 LiDAR/IMU 录制不包含在地图保存包中 |

地图根目录以运行配置 `NAV_MAP_DIR` 为准，默认是当前运行用户的 `~/data/lingtu/maps`。
不要拿开发机 `build/` 下的测试夹具当作机器人上的正式地图。

“保存地图”默认勾选“保存点云后自动后台处理”。取消勾选时，可靠归档后进入 `CAPTURED`
并等待“开始处理”；重启不会自动加工它。自动模式在可靠归档后排队处理，Web 不再要求
等完整图优化、清理和 OctoMap 生成才显示“PCD 已保存”。点云与扫描包写盘及同步仍需时间，
不能承诺大地图瞬间保存。`capture` 之前已有 SLAM 的筛选、去畸变和坐标处理，不是原始雷达录制。
SLAM 保存只生成／发布快照，不再为保存建立 ICP/BBS 重定位索引或替换当前已加载的定位地图。
定位索引由显式加载地图建立；保存过程中当前定位图保持原样。

## 正式地图包

默认保存得到的主要文件如下。部分诊断文件只有对应处理实际产生后才存在。

```text
<map_id>/
  map.pcd                     当前版本的有效点云
  octomap.ot                  当前版本的三维占据地图
  metadata.json               地图及产物说明
  map.before_clean.pcd        首次应用清理前的点云备份
  map.removed.pcd             最近一次清理移除的点
  patches/*.pcd               经过前处理、去畸变后选取的机身坐标关键帧
  poses.txt                   当前关键帧位姿
  poses.raw.txt               图优化前的估计位姿（不是原始传感器数据）
  trajectory.txt              当前估计轨迹
  trajectory.raw.txt          图优化前的估计轨迹
  keyframes.timestamps.txt    关键帧采集时刻
  scan_origin.txt             雷达原点相对关键帧坐标系的位置
  patch_bundle.manifest       关键帧集合及对应关系
  map_optimization.json       图优化结果或未执行原因
```

`map.pcd` 是当前版本的点云，不应称为“完全未处理的原图”。它可能已做图优化、prune，
以及配置要求的体素过滤。导航的三维占据查询使用 `octomap.ot`，恢复点云后需要重新生成对应产物。
接口中的 `map_pcd.role` 相应使用 `saved_map_source`；文件名和 `source_pointcloud` 能力标识不变。

`map.before_clean.pcd` 保留第一次应用清理前的内容；重复执行 `prune --apply --overwrite`
不会覆盖它。`map.removed.pcd` 则会随最近一次清理更新，两者不一定来自同一次运行，
不能一直假定“清理前备份 = 当前点云 + 当前移除点”。

### 文件名调整与旧地图

新的清理前备份叫 `map.before_clean.pcd`，旧名为 `map.pcd.preclean`。
独立 prune 优先复用新名备份，没有新名时复用旧名，不能用已经清理过的地图覆盖原备份。
旧包经正式保存流程重新入库时，已有备份复制到新包的标准名称；该复制沿用原保存事务，
不在用户原目录强制改名，也不另外复制一份同样的备份。

独立 prune 仍生成 `map.clean.pcd`，便于只分析／输出候选结果时审查。
新正式地图包不再额外保留这一中间文件，以 `map.pcd` 为当前点云。
重存旧包时，旧 `map.clean.pcd` 和旧备份名在同一事务内清理，失败会按原事务恢复。

## 一次保存任务

Linux 使用以下布局；目录只有执行到对应步骤时才会出现。

```text
.save_jobs/<job_id>/
  job.state                   当前状态、请求参数、处理报告与恢复记录
  events.jsonl                按时间追加的事件和原因
  capture/                    SLAM 交付并可靠归档的快照；成功后也保留
    map.pcd
    patches/ ...
  work/
    source/                   快照的加工副本
    optimized/                保存时图优化的输出（实际执行时才有）
    maps/<map_id>/            正在生成和校验的候选地图
```

Windows 的 `work` 单独位于 `%TEMP%/lt_maps/<job_id>/`，子目录同样是
`source/optimized/maps`。本地原生状态中的 `job_dir`、`capture_dir`、`work_dir`
提供准确路径；公共 HTTP/Web 不暴露本机绝对路径。

旧的工作区子目录名 `i/o/s` 已改为 `source/optimized/maps`。工作区不是断点恢复输入，
重试会按既有流程清除整个工作区并从 `capture` 重新生成，因此无需改写旧任务的恢复记录。
`capture`、`job.state`、`events.jsonl` 的既有名称保持，便于恢复旧任务。

正式提交还有两个短期事务目录，位于地图根目录，便于同卷替换：

- `.save-staging-<job_id>`：等待提交的完整候选地图。
- `.save-backup-<map_id>-<job_id>`：替换期间的旧正式地图，用于回滚。

这些目录由保存事务处理。不能因为名字带 backup/staging 就在运行中手工删除。
复制快照中断还可能留下 `capture-staging-*`，状态文件写入中断可能留下 `job.state.tmp-*`；
它们是未完成的临时资料，不应当作完整 `capture` 直接重试。本轮没有自动删除已有失败资料。

## 成功、失败、取消和重试

| 结果 | 保存什么 | 后续行为 |
| --- | --- | --- |
| 仅保存，等待处理 | 完整 capture、任务状态与事件 | `CAPTURED` 不自动处理；点击后使用同一任务 |
| 处理成功 | 原始 capture、正式地图、任务状态与事件 | 只清除加工 work 和提交备份，原始归档继续保留 |
| 快照尚未取得就失败 | 任务状态和事件，可能只有部分临时资料 | 重试需要新的完整快照 |
| 优化、清理或地图构建失败 | 已取得的完整 capture 和当时的加工资料 | 原正式地图不被失败结果替换 |
| 校验、提交失败 | capture 以及尚保留的工作资料；必要的回滚证据 | 清理未提交候选并恢复旧正式地图；恢复失败会报告原因 |
| 取消 | 已取得的 capture 和工作资料 | 不提交候选地图；已有完整快照可供重试 |
| 处理／重试处理 | 复用同一个任务的有效 capture | 清除旧工作区和两类旧处理报告，重新加工；不请求新扫描 |
| 进程中断后恢复 | 根据 capture 与提交记录恢复 | 已提交的恢复为成功；未完成的重新排队或等待快照 |

失败／取消状态保留最后实际阶段，只有成功完成才进入 `DONE`。
旧记录已经写成 `DONE` 或状态损坏时，不补造阶段；可以查 `events.jsonl` 的历史事件。
重试前若要保留上次失败的中间结果，应先复制工作区，因为重试会重新生成它。

旧版本成功任务可能已经删除 capture。这些记录返回 `source_saved=false`，不会把最终清理图
冒充原始归档。新流程只有在文件同步、快照回执可靠记录后才确认存档；磁盘写入、快照生成
或接收本身失败时，不能保证有完整 PCD。加工所需的空间检查在加工阶段执行，失败不撤销存档。

旧任务没有完整快照、建图 Product 会话又已改变时，重试返回 `snapshot_session_expired`，
提示重新保存当前地图；不会把新会话的扫描悄悄绑定到旧任务。有完整旧快照的任务仍能
重新处理原数据。快照被拒绝时保留真实失败原因，不继续显示为无限等待。
新的“开始处理”只使用已有归档，可跨 Product 会话调用；它仍遵守当前活动地图不可被覆盖的限制。
对排队、运行或成功任务重复调用返回已有结果，成功任务不会因此再次清理。

同名地图再次成功保存会替换旧正式地图；每次任务的源归档仍分别保留，提交备份仅用于回滚。
若需要同时保留两个可使用版本，应分别保存为不同地图名。

## 如何查看失败记录

Web 地图工具中的“保存记录”独立于已存地图列表，可查询进行中、失败、取消和成功的保存任务。
任务显示地图名、任务标识、时间、阶段、源归档状态和原因；处理／重试／取消只由用户点击触发。
进行中的处理每两秒串行查询一次，待手动处理的 `CAPTURED` 不轮询。原始点云下载按任务身份，
不读取可能仍对应旧版本的同名正式地图。只有处理成功才刷新／选择正式地图库中的结果。
刷新页面后重新查询已有任务，无需重新发起一次保存来找回失败记录。

对应公共 API：

```text
GET  /api/v1/maps/operations
GET  /api/v1/maps/operations/<operation_id>
POST /api/v1/maps/operations/<operation_id>/retry
POST /api/v1/maps/operations/<operation_id>/cancel
POST /api/v1/maps/operations/<operation_id>/process
GET  /api/v1/maps/operations/<operation_id>/source/pcd
```

失败任务不是已验证可导航地图。界面不会因存在 capture 或中间 OctoMap 就把任务标成可加载。
归档下载通过 Linux 原生文件描述符通道流式传送，不暴露本机绝对路径；Windows 原有 FD 通道
仍返回 unsupported_platform。归档状态和手动处理本身可在 Windows 原生测试，文件传送已在 WSL
Linux 验证。原图/清理图切换和一键恢复玻璃尚未实现。

原始归档成功后也保留，因此会增加磁盘占用。本轮没有加入自动删除旧归档的策略。
