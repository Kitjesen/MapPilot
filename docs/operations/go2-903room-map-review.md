## 优化为何跳过

报告为 `performed=false / success=true / sequential_chain_incomplete`，
在 `2→3` 的顺序配准处停止，故只有 2 条顺序约束。`loop_count=0` 表示此次尚未进入
闭环搜索，不能解释成“已经搜索但没有闭环”。`success=true` 是保留未优化地图的
正常跳过结果，不能写成 PGO 已成功优化。

使用实际两帧点云、当前生产配准代码和原门槛离线复现：

| 指标 | 正向 | 反向 |
| --- | ---: | ---: |
| 有效平面对应 | 340 / 1160 = **29.3103%** | 405 / 1112 = 36.4209% |
| 当前最低比例 | 30% | 30% |
| 重叠率 | 98.3393% | 95.6653% |
| RMSE | 0.1473 m | 0.1415 m |
| p95 残差 | 0.2578 m | 0.2438 m |
| 平面信息最小特征值 | 0.06241 | 0.07999 |
| 平面条件数 | 8.203 | 6.650 |

正向平面支持比例不足，其他上述门槛通过；不能因为只差 8 个对应点就降低门槛。
对照的 `0→1`、`1→2`、`3→4` 均通过。`3→4` 自身也有显著姿态变化，因此不能
断言此系统完全不支持机身俯仰或台阶。

用户确认采集中有台阶或明显姿态变化。`2→3` 保存位姿高度增加 0.3069 m、pitch
从 2.733° 变为 11.123°；轨迹精确匹配时间相隔 6.71 秒。配准包含重力对齐，
拟合高度变化约 0.2895 m，未发现“直接忽略倾斜”的证据。不能仅凭这段变化判定
定位故障，也没有通过本次检查证明所有位姿都真实准确。

额外确认了关键帧采样的局限：`fastlio.cpp::recordPatchSnapshot` 只检查 XY 位移和 yaw，

`903room` 保存本身没有切换导航或开始行走；其后的 `.54` 安装已开始新的建图会话。
先检查保存、清理及优化结果，再重新打开地图。当前保存与重开已通过，
但优化跳过的问题尚未通过新采集复测，因此暂不把这张地图作为导航验收图。

采样修复落地后先复测同一小范围路线，以新名字保存，检查顺序约束与优化是否通过。
地图质量检查通过后，才使用网页“使用此地图导航”切换 Product；该操作会结束
当时的建图会话，因此必须先保存需要保留的新扫描。切换后还需确认定位所用的地图
身份、位姿新鲜度及地形/路径可用性，再进行有人监督的短距离导航和停车验证。

## 2026-09-23：BBS3D 集成二次审查

本项目固定原作者 CPU 版 3D-BBS 提交 `41529a34`。现场路径输入是经雷达外参
转换后的机身扫描和同步的机身在 odom 中的姿态；BBS 前先用后者消除扫描的 roll/pitch，
BBS 返回 level 在 map 中的粗位姿，再右乘 body→level 得到机身在 map 中的位姿，最后用**原机身扫描**
做 GICP。此坐标变换次序与上游“重力对齐源扫描、输出源点云在地图中的位姿”约定一致，
合成倾斜扫描和 903room 第 3 帧回放均覆盖了它。

二次审查发现两处会造成错误结论的差异，已改本地源码：
