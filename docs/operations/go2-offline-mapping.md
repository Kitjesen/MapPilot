## 建图、预览、保存

1. 等界面进入建图状态，点云、位姿和传感器时间持续更新。原地观察约 20 秒。
2. 进入 **遥控** 模式，确认控制归属和可用状态，再由现场操作者按键行走。
   升级后先按 `Ctrl+F5` 刷新。第一次按方向键只建立遥控连接；显示已连接后，
   松开并重新按键才开始运动。浏览器快捷键和输入法组合按键不作为运动输入。
   `W/S` 前后、`A/D` 侧移、`Q/E` 转向；松键停车，`Space` 停止。
   建图直接遥控需要人工避让障碍，不能当作已验收的自主避障。
3. 首轮只走一小圈，回到起点并停稳；从不同方向检查地面与墙面覆盖。
4. 点击 **保存地图**，使用新名字，例如 `offline_loop_20260922_01`；等待保存成功，
   再从 **已存地图** 打开该地图，切换 2D / 3D 检查整图。
   实时累计视图仍可能抽样，局部投影仍是局部窗口；最终以保存产物和重新打开的整图为准。
5. 在保持网线连接的情况下刷新页面，重新打开已保存地图，确认它仍存在且可预览。
   地图保存在 NX 的 `/var/lib/lingtu/maps/`，不在浏览器或开发电脑；需要备份时另行下载。

先完成小圈保存与重开检查，再扩大建图范围。进入导航还需要加载地图、定位成功、
检查地形与路径，并做现场运动测试；保存成功不等于导航已验收。

## 点击保存后，系统实际做什么

1. **建立保存任务并冻结快照。** 网页向 mapd 提交任务，由原生 SLAM 冻结当前点云、
   扫描帧、轨迹和雷达原点。任务绑定当前建图会话；冻结后继续采集的新数据不属于
   这次快照，需要以后再保存。网页等待的是任务结果，不负责写地图文件。
2. **尝试全局优化。** 完整扫描包进入原生配准和位姿图优化。自动优化要求完整的
   相邻帧约束链及经过验证的闭环；证据不足时会记录“未执行”及原因，保留未优化源图。
   例如 `floor9` 在 480→481 相邻帧配准处退出，尚未进入闭环验证，
   `loop_count=0` 不能证明真实环境中没有闭环。
3. **清理和过滤源点云。** 使用标定后的雷达原点与多帧射线证据清理残留候选点，
   保存清理前点云、扫描帧和原点，随后按保存配置做体素过滤。现场要求的清理失败时，
   整次保存失败；不能把“没有新回波”直接当成空闲证据。
4. **生成导航文件。** 由同一份处理后的源图生成三维 OctoMap、二维占据图、距离场
   和通行代价图，并检查文件、坐标及地图身份。当前保存二维投影没有独立自由射线输入，
   因而不凭空生成空闲格；三维导航的机身净空和脚下支撑需要单独检查。
5. **事务提交。** 全部必需产物通过后，再提交为地图库中的一个完整版本；提交失败
   会恢复原版本。**用已有名字保存成功会替换原地图，不保留自动历史副本。**
   要保留 `floor9`，必须用新的候选名称。
6. **查看处理结果和整图。** 保存成功只证明文件与事务通过；还应查看优化是否执行、
   清理是否完成。网页等待超时并不等于机载任务失败，应查询原任务，避免另开同名保存。
7. **另行验证导航。** 停稳后通过 ProductControl 加载候选图，完成定位、机身净空与
   地面支撑检查，再做不发送运动目标的路径预览。通过后才进行现场看护下的小范围导航。
   保存任务本身不切换导航、不自动激活地图，也不会发送行走目标。

实现入口见 [原生地图流水线](../../src/maps/README.md)。`.49` 起网页呈现独立的
优化/清理摘要及慢保存待确认状态；继续查询沿用同一个任务，不重新提交保存。
完整现场保存已在 `.50` 验证，实际安装版本与后续修复见下面的本轮记录。

- **验收范围**：已有现场遥控/松键停车反馈，实际是用户主动多次操作、0.50 m/s，
  不是单次 0.20 m/s 定量测试；失联停车、断 Wi-Fi 后持续控制、大地图长期行走、
  实机动态避障仍待验收。控制频率配置 100 Hz 不证明每轮都在 10 ms 内完成。
  有运动异常先通过正式停车入口并核对现场停稳；调试不绕过原生仲裁和 driver。
- **相机**：D435i RGB-D 已有静止数据证据，但 RobotConfig 的相机外参仍
  `unverified`。相机预览不能作为人物跟随、地图坐标精度或 RGB-D 避障已验收的证据。
- **NX 无线**：USB BCM43569 网卡尚未建立可用无线接口；此前临时驱动测试因 USB
  端点描述失败。不能把有 USB 设备或 Go2 自带 Wi-Fi 当作 NX 已无线联网。
  详见 [无线调查](../../build/nx-wifi-20260920/README.md)。
- **磁盘历史**：9 月 20 日的 ext4 元数据错误已在 9 月 21 日离线修复并完成观察，
  不要继续按“尚未修复”处理，更不要在挂载中的根分区重复 fsck。后续若出现新 I/O
  错误再针对处理。见 [修复记录](../../build/go2-repair-20260921/README.md)。
- **平台边界**：这里是 Go2 + NX + MID-360 + D435i 的证据，不是 S100P/RDK X5
  验收。建图与导航分别使用 `map` / `nav` Product；机载链路是原生 DDS，
  `navd → lingtu-driver → Go2 SDK`，不另起竞争的传感器采集或运动出口。

## 开发电脑恢复维护连接

小电脑需同时保留 Wi-Fi 和到 NX 的网线。先按故障位置检查：跳板 SSH 不通就核对
小电脑 Wi-Fi/地址；跳板在线但 NX `22` 不通则看有线适配器状态、`.100/24` 路由和
NX 电源。历史曾出现“以太网 2：网线断开”。本机转发端口监听不等于 NX 可达。

以下是从历史成功命令整理的两跳方式；只建立连接，不切换 Product。小电脑 SSH
曾使用设备已有密码，不能假定 NX 的部署密钥也已授权给 `dz`。本文不存储密码或私钥。
在开发电脑单独终端运行，保持该终端打开：

```powershell
ssh -N -o StrictHostKeyChecking=yes -o ExitOnForwardFailure=yes -o ServerAliveInterval=20 -o ConnectTimeout=6 -L 127.0.0.1:12218:192.168.123.18:22 -L 127.0.0.1:15052:192.168.123.18:5050 dz@192.168.66.95
```

然后在另一个开发电脑终端通过 NX 已授权的部署密钥登录：

```powershell
ssh -o StrictHostKeyChecking=yes -o HostKeyAlias=192.168.123.18 -o ConnectTimeout=6 -i "$env:USERPROFILE/.ssh/inovxio_deploy" -p 12218 unitree@127.0.0.1
```

本机历史私钥路径为 `C:/Users/99563/.ssh/inovxio_deploy`。`HostKeyAlias` 将转发
端口对应到已知 NX 主机身份；换端口不应被误认为换了机器人。
登录后先 `readlink -f /opt/lingtu/current`，再按上文加载部署环境、执行只读
`scripts/lingtu ... status`。不要因为网页没启动就隐式切换正在工作的 Product。
检查传感器/遥控问题时先读现有状态和 SHM，避免启动第二套采集程序占用设备。

常用位置：

| 路径 | 用途 |
| --- | --- |
| `/opt/lingtu/current` | 当前不可变发布目录的符号链接 |
| `/opt/lingtu/config/go2-native.env`、`python.env` | 部署环境与项目 Python；系统旧 Python 不一定满足要求 |
| `/var/lib/lingtu/maps/floor9/` | 原始保存地图 |
| `/home/unitree/outdoor-teleop-20260922/` | NX 本轮回放、构建、安装和验收证据 |
| `/home/unitree/outdoor-teleop-20260922/maps48-review/floor9_review_20260922` | 尚未激活的重建地图副本 |
| `/home/unitree/lingtu-candidate-dynamic-20260920` | 先前导航 ARM 构建树；不等于当前安装目录 |
| `/tmp/lingtu_slam_status.json` | SLAM 状态，读取时核对时间新鲜度 |
| `/dev/shm/lingtu/nav_endpoint_status.json` | 原生导航、仲裁、最终指令和运行状态 |

NX 上曾用的旧 CTest 不支持 `--test-dir`，应进入对应 build 目录运行；
“No tests were found”不计为通过。新增 CMake 测试目标后需先重新 configure。
