# LingTu 产品说明

**Status:** Current product scope; field qualification remains in progress
**Audience:** 产品负责人、机器人操作员、交付与集成工程师
**Runs on:** 按 RobotConfig 选择的 `env=real` 或 `env=sim`

LingTu 为四足机器人提供建图、保存地图、定位和自主导航。当前交付重点是让同一台
机器人在一份确定的地图上反复完成这条流程，并能停止、取消任务和接受人工接管。
巡检、语义任务与楼梯通行在此基础上扩展，各自需要单独验收。

**代码已实现不等于产品已验收。** 当前任务、失败记录和下一步统一维护在
[路线图](roadmap.md#current-delivery-cycle)；本页定义交付范围，不重复维护测试结论。

## 用户需要理解什么

网页应围绕三个事实组织操作：**当前模式、所选地图、机器人运行状态**。
操作员选择模式、地图和目标；系统负责启动对应服务、规划、执行和反馈结果。
RunPlan、Host 组装和进程排序属于内部实现，无需成为现场操作的步骤。

| 要完成的事 | 用户操作 | 系统反馈 |
| --- | --- | --- |
| 创建地图 | 进入建图，遥控采集后保存 | 保存进度、成功或失败、候选地图 |
| 使用已有地图 | 选择地图并进入导航 | 地图加载与定位状态 |
| 去一个位置 | 点选目标，查看自动生成的路线，点击开始导航 | 规划结果、执行状态、到达或受阻原因 |
| 连续到达多个位置 | 添加连续点，检查顺序后开始 | 当前点、路线进度、最终结果 |
| 临时人工接管 | 使用受支持的网页、键盘或游戏手柄入口 | 当前控制来源及保留任务状态；释放后显式继续 |
| 结束运动 | 取消任务或使用停止操作 | 任务结果与实际停车状态，分别显示 |

点选和路线预览不提交运动。状态文字必须来自实际状态，不能把“请求停车”显示成
“已经停稳”，也不能仅凭受阻原因显示“任务已暂停”。具体入口和恢复操作见
[现场操作](operations.md)。Go2 原厂手柄仍需完成固件与接管行为核查，不能承诺与
网页输入相同的任务恢复语义。

## 完整交付流程

| 阶段 | 完成这一步需要看到什么 | 负责说明 |
| --- | --- | --- |

| 建图 | 当前扫描和位姿持续更新，采集范围覆盖预期路线 | [现场操作](operations.md) |
| 保存、清理、构建 | 保存操作成功；完整地图包和派生 OctoMap 可加载；原始数据可追溯 | [地图模块](../src/maps/README.md) |
| 重载与定位 | 选择的地图与运行地图一致；重启后定位可用 | [现场操作](operations.md) |
| 路线预览 | 同一地图、规划参数和固定目标下返回路径或明确失败原因 | [测试与证据](testing.md) |
| 导航与接管 | 路线跟踪、局部避障、受阻恢复和人工接管按实测结果工作 | [现场操作](operations.md) |
| 结束与再运行 | 到达、取消或停止后输出归零；下一次任务能正常开始 | [测试与证据](testing.md) |
| 发布与维护 | 整包安装、配置保留、失败恢复与支持范围有记录 | [部署说明](../scripts/deploy/README.md) |

地图显示的高度裁剪只影响查看。隐藏天花板、显示地形或调整点云颜色，不改变保存
地图、三维碰撞和导航输入；点云空白也不能作为可通行的证据。

## 现有能力和交付边界

| 能力 | 当前实现 | 交付时仍需确认 |
| --- | --- | --- |
| 建图与地图管理 | 原生 SLAM、mapd、保存清理、OctoMap 构建及地图选择 | 同一真实地图的保存、重载、定位和导航完整流程 |
| 三维导航 | OctoPlanner3D 全局路线、SCAN 局部轨迹与避障、导航执行与恢复 | 固定路线回归、真实受阻、取消、停车和再次导航 |
| 连续点与巡检 | 地图绑定路线、原生点位推进和观察/证据接口 | 重复巡检、断点继续、结果可信度及现场连续运行 |
| 人工接管 | 原生控制权管理和网页、键盘、游戏手柄输入 | 在命名机器人上验证接管、释放保持、任务继续和取消 |
| 相机与语义任务 | 可选相机模式、感知接口和地图语义数据 | 选定模型、标定、设备判读与目标识别的实际效果 |
| 录制与回放 | 原生 DDS/MCAP、相机片段、网页会话管理与传感器播放器 | 同一录制输入替换实时源后的算法重算、时间一致性和结果对照 |
| 楼梯 | 标注、识别与模式切换的开发和仿真验证路径 | 上下楼物理能力、模式确认和出口恢复；不能据此宣称实机可用 |
| 批量部署 | 单机发布和生命周期机制 | 设备清单、地址与隔离、分批安装、结果汇总和批量恢复 |
| 返航与充电 | 可规划返回待机点的流程 | 当前无自动充电桩验收；到达待机点不等于已充电 |

具体缺口见[路线图](roadmap.md)。常规建图和导航不以语义模型服务为前置条件。
单次成功只证明该版本、地图、配置和场景；无人值守与长期连续运行需要另外的证据。

## 机器人和运行环境

机器人通过 [RobotConfig](../config/robots/README.md) 选择，设备和标定随平台维护。
现有目录包含 `unitree/go2` 与 `doso/thunder_v4` 的真实配置；Thunder 有仿真配置，
Go2 仿真资产与预设仍有缺口。配置存在不等于该组合已完成验收。

真实部署使用声明的 Linux/CycloneDDS 合同及对应平台的整包。Windows 开发结果、
Linux/WSL 结果和真实控制器结果分别记录。MuJoCo 适合验证任务与执行流程，不能
替代真实传感器、网络、外参或步态验证。见[仿真](simulation.md)。

## Web 与机器人职责

Web 在操作电脑的浏览器中渲染地图、显示状态和提交操作；机器人侧 Gateway 提供
接口，ProductControl 管理运行模式，原生服务负责定位、导航、驱动和录制。
录制的数据在机器人侧采集保存，Web 管理录制会话和下载结果。

前后端通过 HTTP、SSE 和 WebSocket 分工。机器人服务包与静态 Web 包分别构建和
打包，沿用同一套 Gateway 接口。Gateway 可通过 `LINGTU_WEB_DIST` 托管独立的
Web 安装目录；更新机器人版本不必替换网页。操作电脑独立托管时，需要同源代理和
相机媒体网络配置；具体安装与升级顺序见[部署说明](../scripts/deploy/README.md#deploy-the-web-ui-independently)。
拆包不代表不同版本可以任意组合，交付时仍要记录并测试对应的前后端版本。

录制与回放沿用[原生录制模块](../src/native/recording/README.md)。录制内容是否完整、
播放是否成功、算法能否用这些输入重现原问题，是分别需要验证的结论。

## 产品交付需要留下什么

每次交付保留一组可对应的发布包、RobotConfig/设备标定、地图与原始采集数据、
实际生效参数、验证报告和安装/恢复记录。报告写明代码或构建来源、目标平台、
地图版本及测试范围；脏工作区的提交 SHA 不能单独代表实际被测代码。
记录格式沿用[现有证据约定](testing.md#evidence-record)，不另建一套交付状态系统。

发布前还需明确支持的机器人与功能组合、已知限制、操作者指南、升级/恢复方式和
第三方组件的分发许可。这些待办统一进入[路线图](roadmap.md)，不在多个文档中
重复维护完成状态。待发布材料先在本地审阅，按现有约定获得确认后再上传。
